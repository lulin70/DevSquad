## 二、Kanban 适用性分析

### 2.1 Kanban 的核心价值

Kanban 适合"任务流可视化"——多个任务在不同阶段间流动，团队成员可直观看到瓶颈。典型场景：
- 项目管理：Story → To Do → In Progress → Review → Done
- 工单系统：New → Assigned → In Progress → Resolved → Closed
- 持续交付：Build → Test → Stage → Deploy

### 2.2 DevSquad 的任务模式

DevSquad dispatch 是**单任务、分钟级、同步完成**的：
- 用户提交一个任务 → 7 角色并行执行 → 共识结论 → 返回报告
- 任务生命周期：P1-P11 阶段，但单个 dispatch 通常在几秒到几分钟内完成
- 不存在"多个任务在不同阶段间流动"的场景

### 2.3 现有视图对比

| 视图 | 数据源 | 展示内容 | 与 Kanban 重叠度 |
|------|--------|---------|----------------|
| `StreamlitDashboard` phase visualization | dispatch 历史 | 11 阶段进度条 | 中（阶段=列） |
| `V43DashboardPanels` | 运行时状态 | 4 面板（Ponytail/Loop/Plugin/TechDebt） | 低 |
| `DAGVisualizer` | 代码结构 | 依赖图（Mermaid/JSON/DOT） | 低 |
| `HistoryManager` 列表 | SQLite 历史 | dispatch 历史表格 | 高（任务列表=Kanban 卡片） |

**结论**: 现有 `HistoryManager` 列表视图已覆盖"dispatch 历史查看"需求。Kanban 若展示 dispatch 历史，则是列表视图的视觉变体，价值有限。

## 四、缓办判定

### 4.1 判定结论

**缓办**。理由：

1. **前置条件未满足**：两轮用户测试中，第一轮（V4.4.1）无 Kanban 需求反馈，第二轮（V4.5.0）未开始
2. **数据源未定义**：Kanban 展示什么未明确，强行实现会产生歧义代码
3. **与现有视图重叠**：HistoryManager 列表 + phase visualization 已覆盖主要需求
4. **YAGNI 原则**：无用户需求驱动的功能属于"为覆盖率而功能"

### 4.2 推迟到 V4.6.0

V4.6.0 实施条件（全部满足才实施）：
- [ ] V4.5.0 多语言 prompt 上线后，至少 2 个用户主动反馈需要 Kanban 视图
- [ ] 明确 Kanban 数据源定义（dispatch 历史 / 11 阶段 / 项目管理）
- [ ] 证明与现有 phase visualization + HistoryManager 列表不重复
- [ ] 7-Role 再次审核通过
