## ⚠️ Read This First — Two Outward-Facing Changes

Per PRD R10-2, the two changes below **must be stated explicitly and are not allowed to be silent**. Everything else in this release is either an internal gate fix or a documentation-truth correction.

### 1. New dispatch mode and new input contract: `mode="review"` + `changeset`

| | Before V4.5.20 | From V4.5.20 |
|---|---|---|
| `--mode` / `mode=` accepted values | `auto` / `parallel` / `sequential` / `consensus` | those four **+ `review`** |
| File input to dispatch | none | `changeset: list[str] \| None = None` (CLI `--changeset <files...>`) |
| Observable result | — | `result.details["review_bundles"]` (also emitted in CLI JSON output) |
| RBAC | — | `review` allowed for **admin / operator**; **viewer is unchanged** (`auto` only) |

`FileBundler` was announced as delivered in V4.5.0, but the inputs the announcement depended on (`mode="review"` and a file/changeset argument) **did not exist anywhere in the dispatch pipeline**. `Coordinator.apply_file_bundling()` therefore had **no production caller for 19 releases**. V4.5.20 builds the missing input path:

```bash
devsquad dispatch -t "review this changeset" \
    --mode review \
    --changeset src/a.py src/b.py src/c.py \
    --backend mock --format json
```

```python
result = disp.dispatch(
    task_description="review this changeset",
    mode="review",
    changeset=["src/a.py", "src/b.py", "src/c.py"],
)
print(result.details["review_bundles"])
```

Backward compatibility: with `changeset=None` or any mode other than `review`, behaviour is **unchanged from V4.5.19** (covered by a dedicated backward-compatibility test). See [V4.5.0_RELEASE_NOTES.md](V4.5.0_RELEASE_NOTES.md) for the in-place amendment to the original (overstated) V4.5.0 verification claim.

### 2. Review-mode bundling behaviour for >5 files

| | Before V4.5.20 | From V4.5.20 |
|---|---|---|
| Review mode, ≤5 files | single bundle (guard) | **unchanged** — single bundle |
| Review mode, >5 files | single bundle **only** (bundling never actually ran) | bundling engages → **one bundle per file group** |
| Grouping rule | — | `FileBundler`: same directory → same bundle; import-linked files → same bundle |

> **Measured wording (not a marketing shorthand).** Bundle **count is decided by directory/import grouping, not by file count**. Real CLI runs recorded in the PRD:
> - 8 files across 3 directories (`pkg_a`/`pkg_b`/`pkg_c`) → **3 bundles**
> - the same 8 files all placed in one directory (`scripts/`) → **1 bundle**
>
> An unconditional claim of "more than 5 files ⇒ multiple bundles" is **false** and was corrected in this release across the six external documents that had stated it.

## What's New

### W0-1 — Sub-skill version drift repaired (11 sites)

Eight `version:` fields and three `version_source:` fields under `skills/*/skill-manifest.yaml` had drifted up to **18 releases** behind the SSOT (e.g. `3.7.2` / `3.9.2` / `4.2.1`). All 11 are now aligned with `scripts/collaboration/_version.py`. `skills/dispatch/skill-manifest.yaml` also had its description corrected from "4 modes" to "5 modes".

### W0-2 — Version-consistency gate blind spot closed

`scripts/check_version_consistency.py` gained `_check_sub_skill_manifests()`: every `skills/*/skill-manifest.yaml` is now a **blocking** check for its `version`, plus a second check when it declares `version_source`. The manifest list is read at **runtime** (`glob`) — no hard-coded check count anywhere. Gate coverage: 77 checks (73 passed / 4 skipped) versus 64 before this release.

Negative test `T16_SubSkillManifestChecks::test_main_exits_nonzero_when_manifest_drifts` proves the gate can go red: a tampered manifest makes `main()` return 1.

### W0-3 — The orphaned review bundling is now real (F4)

| Step | Change |
|---|---|
| W0-3a | `cli_utils.MODES` + `dispatch_rbac.ALL_DISPATCH_MODES` accept `review`; operator set `{auto, parallel, sequential, review}`, viewer still `{auto}` |
| W0-3b | `MultiAgentDispatcher.dispatch(changeset=...)`, threaded through `**kwargs` → `pre_dispatch.execute(...)` → `prepare_execution(...)`; no global config, no env var |
| W0-3c | `prepare_execution()` routes `mode == "review" and changeset` to the bundle plan; all other paths untouched |
| W0-3d | New `Coordinator.plan_review_bundles()` — the **only** caller of `apply_file_bundling("review", changeset)` |
| W0-3e | Bundle split is observable via `result.details["review_bundles"]` + CLI `--changeset` + JSON output |
| W0-3f | The pseudo-e2e that `import`ed `FileBundler` directly was deleted and replaced by two tests that reach the real `dispatch()` path |

### W0-4 — Anti-ghost gate no longer accepts its own calls (D7)

The gate's `main()` bumped 30+ module counters via **direct calls before any production pipeline ran**, so its `counter > 0` assertion was satisfied for *every* module — a structural design flaw, and precisely why `FileBundler` could stay green while being a ghost. This is now fixed:

- **Production probe first**: the gate runs a real `MultiAgentDispatcher.dispatch()` (`auto` + `review` with a 6-file changeset) before any self-call and records the delta.
- **Assertion replaced**: modules in `PRODUCTION_WIRED_COUNTERS` must be bumped **by the probe**; otherwise `FAIL (self-call only)` and exit 1. The counter must also still be positive — the pre-existing fail-closed contract for non-positive counters was preserved (an existing e2e caught an early regression here; the **source was fixed, not the test**).
- **Honest reporting**: modules outside the set keep their old semantics but are now labelled `PASS (self-call)` instead of implying production evidence.

```
Anti-ghost gate PASSED: 8/8 production-verified, 27 self-call verified.
```

Two verifications: a deliberately mis-declared module (`MokaAIBackend_P12.1.1`, measured `delta=0`) turns the gate red; and **reproducing the exact F4 failure mode** (forcing `changeset=None` back to the V4.5.19 state) is caught precisely as `FAIL (self-call only)` for `FileBundler_V450` — which the old gate would have passed. Permanent regression: `tests/test_check_module_activation.py::T3_F4Regression`.

### W0-6 — Test-name discipline gate

F4 hid for 19 releases partly because an "e2e" test was named `..._activates_in_review_mode` while its body imported the module directly. `check_module_activation.py` now scans the real `tests/e2e` tree: a test whose name claims *activation* must reach a production entry point. The check is AST-based — mentioning `dispatch()` in a docstring is **not** evidence. Five tests cover it, including a negative case built from the original F4 shape.

## Known Boundaries (disclosed, not defects)

| Boundary | Detail |
|---|---|
| `--dry-run` does not show bundle splits | `dispatch()` short-circuits at `pre_result.early_return`, so `prepare_execution()` is never reached and no bundle plan is produced (`review_bundles: null`). Observed, not inferred. |
| MCP `multiagent_dispatch` does not expose `changeset` | The MCP tool signature is unchanged; review bundling is reachable through the CLI and the Python API only. |
| 27 anti-ghost counters still self-call | They are now honestly labelled `PASS (self-call)`. Wiring each one to a production probe is a separate work item (needs a per-module judgement on whether a dispatch path genuinely exists) and is **out of scope** for this release. |
| `tests/external/test_real_llm.py` — 2 items fail on this machine | Both request `api.openai.com` directly with no key fixture. In the local sandbox the socket connect hangs and `pytest-timeout` fails them. `git status --short tests/external` is empty (zero overlap with this changeset) and GitHub Actions has outbound network, where the request returns 401 and the assertion holds. **Neither the tests nor the source were changed.** |

## Upgrade Notes

- No migration required. With `changeset` unset, dispatch behaves exactly as in V4.5.19.
- To use review bundling, call `--mode review` **with** `--changeset`; a review dispatch without a changeset deliberately falls back to the V4.5.19 single-plan path.
- SemVer: 4.5.19 → **4.5.20** (MINOR), per PRD §7.1 (R10). The working label `4.5.20` used throughout design and implementation is the released number.
