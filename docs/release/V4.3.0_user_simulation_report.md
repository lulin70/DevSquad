## 4. 痛点 Top 3（基于 E2E 测试中遇到的 frictions 推断）

### 痛点 1：7-Role dispatch 在 Mock 模式下仍需 0.26s
- **现象**: PM 旅程 `test_01` 单次 dispatch 耗时 0.26s，是其他旅程的 13×。
- **根因**: 7 个 Worker 即使在 Mock 模式下也要走完 Coordinator / Scratchpad / Consensus / Compression 等完整 pipeline。
- **影响**: 真实用户在交互式 CLI 中可能感到轻微延迟（<1s 可接受）。
- **建议**: V4.3.1 评估是否在 Mock 模式下短路 Consensus/Compression 阶段。

### 痛点 2：`ComplianceReport` 缺少 `to_markdown()` 方法
- **现象**: 运维旅程验证了 `lifecycle_gate_check` 的合规/违规判定，但运维用户无法直接获得格式化报告——只能通过 `to_dict()` 序列化 dict。
- **对比**: `DispatchResult` 有 `to_markdown()`，`DependencyScanResult` 有 `to_markdown()`，唯独 `ComplianceReport` 缺失。
- **影响**: 运维用户需手动拼装 Markdown，体验割裂。
- **建议**: V4.3.1 为 `ComplianceReport` 添加 `to_markdown()`，渲染「部署合规」章节。

### 痛点 3：`security_scan_dependencies` 模块级调用计数器不利于并行测试隔离
- **现象**: `get_call_count()` 是模块级全局变量，开发者旅程用 `before/after` 比对验证递增，但若并行测试同时调用，比对会受干扰。
- **影响**: 当前 E2E 串行执行无问题；未来若开启 `pytest-xdist` 并行执行可能出现 flaky。
- **建议**: V4.3.1 评估是否改为实例级计数器或提供 `reset_call_count()` 测试辅助。
