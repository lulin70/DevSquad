## 2. 背景与目标

### 2.1 背景

DevSquad V4.2.1 已具备 7400+ CI 测试、稳定的技术债基线（真实可执行 TODO 数 = 0）。在 V4.2.1 发布后，PM 主导整合三方面输入，制定 V4.3 统一推进路线。三方面输入及其现状基线如下：

| # | 输入来源 | 现状基线 | 关键发现 |
|---|----------|----------|----------|
| 1 | **技术债跟踪** ([TECH_DEBT.md](../TECH_DEBT.md)) | 1 项 P3 信息性条目，无真实可执行 TODO | 基线干净，但缺少"持续监控 + 入门文档"闭环机制 |
| 2 | **pickle→JSON 迁移** (`cache_interface.py`) | 4 处 pickle 使用（2 处 dead code + 1 处 fallback + 1 处文档残留） | 可分两阶段安全迁移；fallback 被 Redis 调用需安全收紧 |
| 3 | **上游 TraeMultiAgentSkill v2.6-v2.8 启发** | DevSquad 已有 Ponytail/Autonomous/Loop/UIUX/PluginHotLoader 基础实现 | 6 个精细化点中 2 项已对齐、3 项可借鉴升级、1 项违反 YAGNI 降级 |

7-Role 已完成共识评估（7/7 APPROVE_WITH_CONCERNS），按 10 项调整修订后达成共识，用户已确认方案 v1.2。

### 2.2 核心目标

1. **消除安全债**: pickle→JSON 迁移完成，移除 `pickle.loads` 反序列化风险面（OWASP A08:2021）；fallback 安全收紧并最终移除
2. **精细化升级**: 借鉴上游 v2.6-v2.8 的 4 个可借鉴点（Ponytail/Loop/UIUX/Dashboard 可视化），将 V4.0.0 基础实现升级为生产级
3. **技术债持续治理**: 建立"扫描-登记-修复-验证"闭环流程，避免技术债再次积累
4. **保持 SemVer 合规**: MINOR 版本递增（V4.2.1 → V4.3.0），所有变更为向后兼容的功能新增

### 2.3 版本策略

采用两阶段发布策略，遵循"文档先行 + 发布前 E2E + 真实用户模拟测试"铁律：

- **V4.2.9** (PATCH 预发布): 全部 P0 + P1 + P2 代码 + 文档同步完成，通过 E2E 测试 + 真实用户模拟测试，等待用户确认
- **V4.3.0** (MINOR 正式版): 用户确认 V4.2.9 后，升 MINOR 号发布
- **P2-1 已并入 V4.3.0**（用户指示合并推进，不再单独 V4.3.1）
- 遵循 SemVer 规则: MINOR 递增仅用于向后兼容的功能新增

## 4. 用户故事

> **格式**: As a \<角色\>, I want \<能力\>, so that \<价值\>
> **遵循 INVEST 原则**: Independent / Negotiable / Valuable / Estimable / Small / Testable
> **覆盖角色**: Security / DevOps / Coder / Architect / Tester / UI Designer / PM

### US-1 (P0-1, Security)
As a **security reviewer**, I want the pickle fallback in `cache_interface.py` to be security-tightened (require Redis password or opt-in default off), so that the Redis-network RCE attack surface via `pickle.loads` is closed even before the fallback is fully removed.

### US-2 (P0-1, Coder)
As a **coder**, I want the 2 dead code pickle branches deleted from `cache_interface.py`, so that the codebase no longer carries unreachable serialization paths that mislead readers and inflate maintenance cost.

### US-3 (P0-2, DevOps)
As a **DevOps engineer**, I want `todo_drift_monitor.py` integrated as a blocking pre-commit hook and CI lint job, so that any new TODO/FIXME/HACK not registered in TECH_DEBT.md is automatically rejected before merge.

### US-4 (P0-2, PM)
As a **PM**, I want the PR template to include a "no unregistered tech debt" reviewer checkbox, so that tech debt governance becomes an explicit review gate rather than an implicit hope.

### US-5 (P1-1, Coder)
As a **coder**, I want Ponytail to support `lite`/`full` dual modes while keeping `full` backward-compatible with V3.10.0 output, so that test/UI roles get a lightweight ruleset without breaking the 17 existing assertions.

### US-6 (P1-1, Architect)
As an **architect**, I want `PonytailDebtCollector` to distinguish "has upgrade path" debts from "rot risk" debts via `# ponytail:` markers, so that the team can prioritize refactor candidates by risk rather than by volume.

### US-7 (P1-4, Tester)
As a **tester**, I want `RollbackStrategy` to map each Loop failure stage (D1-D6) to a precise rollback target, so that a failed iteration retries from the correct stage instead of always restarting from DEVELOPMENT.

### US-8 (P1-4, Architect)
As an **architect**, I want an independent `rollback_max_iterations` hard cap (default 3) separate from `max_iterations` (default 50), so that runaway rollback loops are stopped early without weakening the normal iteration budget.

### US-9 (P1-5, UI Designer)
As a **UI designer**, I want a living `V43_UIUX_SUBITEM_COMPARISON.md` audit document comparing DevSquad's UIUXAnalyzer against upstream v2.7 across all 4 dimensions, so that I can prove where DevSquad leads and objectively identify any missing sub-items to backfill.

### US-10 (P1-6, UI Designer)
As a **UI designer**, I want the Dashboard to visualize Ponytail mode, Loop rollback status, and Plugin hot-reload events, so that V4.3 backend capabilities become perceivable to end users instead of invisible internals.

### US-11 (P2-1, Security)
As a **security reviewer**, I want the pickle fallback fully removed after a 7-14 day observation period confirms no legacy pickle payloads remain, so that the OWASP A08:2021 deserialization risk surface is eliminated entirely.

### US-12 (P2-2, PM)
As a **PM**, I want the Autonomous SmartConfirmation three-state decision logic documented in a dedicated guide, so that users can confidently configure smart/whitelist-only/blacklist-only modes without reading source code.

## 7. 风险与依赖

### 7.1 风险

| 风险 | 等级 | 缓解措施 |
|------|------|----------|
| pickle 迁移破坏遗留缓存 | 低 | P0-1 仅删 dead code + 安全收紧；P2-1 有 7-14 天观察期 |
| pickle fallback 被 Redis RCE 攻击 | 中 | P0-1 强制 Redis 密码或 opt-in 默认关闭；一次性 payload 扫描 |
| Ponytail 模式切换破坏现有行为 | 低 | 保留 `full` 模式为默认（PONYTAIL_RULES 原文本），与 V3.10.0 行为一致 |
| LoopKernel 回退策略误判 | 中 | 独立 `rollback_max_iterations` 硬上限 3 次，超限自动 STOP_FAILURE |
| CI 测试数下降（pickle 测试移除） | 低 | 同步新增迁移验证测试，保持总数 ≥7400 |
| 文档同步遗漏 | 低 | `check_config_consistency.py` CI 门禁 |
| `test_contains_all_7_rungs` 断言破坏 | 低 | P1-1 同步参数化修改（已声明） |
| Dashboard 新增视图视觉回归 | 低 | P1-6 建立视觉回归 baseline |
| P2-1 观察期内发现遗留 pickle 缓存 | 低 | 延长观察期或提供迁移脚本，不强制删除 fallback |
