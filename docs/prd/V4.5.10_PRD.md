> 状态：P2 修订中（初审未通过，已补充协议/安全/测试硬约束，待三贤者复审）  
> 基线版本：V4.5.9（commit `4f954a2` / tag `v4.5.9`）  
> 收口跟进：`37f973b`（release-e2e 复用化 + 发布硬依赖）、`fc18850`（CHANGELOG 记录）

## 0. 评审反馈与不可变决策

初审评分：架构 7.3/10、测试 7.0/10、安全 5.5/10，均未达到 8.5 门禁。本轮修订采用以下不可变决策：

1. **协议兼容优先**：v2 marker 严格保持上游 v2.8.4 的 7 个字段：`request_id`、`agent_type`、`task`、`request_file`、`prompt_file`、`timeout_seconds`、`timestamp`。不新增 `protocol_version` 字段；协议版本由目录和 marker 文件名表达。
2. **完全隔离**：v1 使用 `<root>/v1/protocol.marker`，v2 使用 `<root>/v2/protocol.v2.marker`；request、prompt、response 和清理操作均限制在各自目录。v2 初始化不得读取、重命名、删除或消费 v1 文件。
3. **配置 fail-closed**：`DEVSQUAD_V455_DISABLE_HOST_BRIDGE_V2=1` 最高优先级；版本配置只接受 `v1`/`v2`（忽略首尾空白、大小写不敏感）；非法非空值直接 `ValueError`，不得静默采用 v2。
4. **回退只发生在创建阶段**：`auto-fallback` 仅可在 v2 adapter 构造或创建前可用性检查失败时选择 v1/A/C。请求发出后不得复制到另一协议重试，避免重复执行；timeout/failure 只返回当前协议的失败结果并记录可回滚信号。
5. **本地 IPC 边界**：HostLLMBridge 默认仅使用同机文件 IPC；bridge 根目录及版本目录为 `0700`，创建的文件为 `0600`。本版不引入网络 listener、端口或远程信任模型。
6. **路径与资源边界**：`request_file`、`prompt_file`、`response_file` 必须是对应版本目录下的 canonical regular file；拒绝绝对越界路径、符号链接、目录和 TOCTOU 后路径变化。prompt 和 request JSON 大小必须有明确上限，超限 fail-closed。
7. **测试证据优先**：门禁必须证明实际 adapter 类型、实际目录/marker、实际 subprocess round-trip、回退优先级、跨版本不可串读、资源边界和 `--async` 实际调用路径，而不是只统计用例数量。

## 1. 背景与问题

### 1.1 HostLLMBridgeV2 已实现但未接入生产（G-α）

`scripts/collaboration/host_llm_bridge_v2.py` 已具备上游 v2.8.4 协议的七字段 marker、独立 prompt 文件、`request_file` 越界校验与原子写，但 `create_backend("host"/"auto"/"auto-fallback")` 仍只实例化 v1 `HostBridgeBackend`。trae 协议若升级到 v2.8.4 监听方，将持续 timeout。

### 1.2 v2 request JSON 仍内嵌 prompt（G-β）

v2 `create_request()` 同时把完整 prompt 写入 `request_{id}.json` 与 `request_{id}.prompt`，与独立 prompt 文件的设计目标相悖。

### 1.3 v2 无 E2E / FakeHostRunner 不兼容 v2（G-δ）

`tests/fakes/fake_host_runner.py` 硬编码 v1。v2 端到端行为（marker 协议、response 字段 `timestamp`）尚未在隔离子进程中验证。

### 1.4 v1/v2 共存风险（G-θ）

v1 与 v2 当前共享默认目录和 `protocol.marker`。v2 初始化会主动迁移 v1 marker，存在并发丢请求风险。

### 1.5 `--async` CLI 缺失（P2-2）

Python API 已有 `async_dispatch` 与 `DEVSQUAD_USE_ASYNC=1`，但 CLI 入口不暴露显式异步路径，运维与脚本无法以参数控制。

### 1.6 文档同步与归档（P1-1 / P1-2 / P2-4 / P2-5 / P3-2 / P3-3 / P3-4）

ALERT_RULES / RUNBOOK / ROLLBACK 停留在旧版本；PROJECT_STATUS / README / SKILL.md 元数据漂移；异常处理、性能监控和 SmartConfirmation 文档未反映当前事实；旧 roadmap 已被 V4.5.7/8/9 替代。

## 3. 范围与子任务

### 3.1 Wave 1：v2 协议补完与隔离（G-β / G-θ）

- v2 request JSON 删除 inline `prompt`，保留 `prompt_file` 指针；reader 兼容历史 inline prompt

- v2 默认目录为 `logs/host_llm_bridge/v2/`，v1 默认目录为 `logs/host_llm_bridge/v1/`
- v2 初始化停止迁移 v1 marker

- `host` / `auto` / `auto-fallback` 默认选择 v2；`host-v1` / `host-v2` 显式选择

## 6. P2-1 / P2-2 正式裁决

### P2-1：SQLite risk store

**裁决：JSON-only long-term，SQLite 不进入 V4.5.10。**

理由：当前 FileRiskStore 已覆盖目标规模和跨进程原子写；现阶段主要风险是协议、生产接线和文档漂移，不是查询性能。引入 SQLite 将新增 schema migration、双后端兼容和锁语义维护成本。只有在容量、复杂查询、远程共享或多服务并发需求被真实数据证明后重新立项。

### P2-2：`--async` CLI

**裁决：纳入 V4.5.10，实现显式 `--async` / `--no-async`。**

选择优先级固定为：

```text
--async > --no-async > DEVSQUAD_USE_ASYNC > 默认同步
```

两个显式 flag 互斥；未指定 CLI flag 时才读取环境变量；环境变量仅接受既有 truthy 语义；最终必须通过真实调用路径和子进程 E2E 证明，而非只验证 parser。
