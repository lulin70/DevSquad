## 1. 背景与来源

### 1.1 借鉴对象与范围声明

上游 v2.11.0（2026-10-12）发布"业务动线分析与页面设计闭环"，把页面级业务质量问题编号化为
两个**封闭集合**：5 类逻辑断点（BREAK-1~5）+ 5 类业务线漏洞（VULN-1~5），并强制
"每个分析必须有采集产物或代码证据，禁止凭空推断"。

本批次**借鉴的是方法论，不是实现**：上游的检测对象是黑盒 Web 页面（Playwright BFS 采集），
与 DevSquad 的 review 模式（代码 changeset、确定性 regex 检查器）场景不同。移植的是三件事：

1. **编号化分类学**——封闭集合 + 每类明确定义，与本仓 `failure_taxonomy.py` 的
   `FailureClass`（product_failed / environment_blocked）同构；
2. **结论必须挂证据**——每条发现必须给出代码位置（file:line）与命中模式名，禁止无证据断言
   （与本仓"audit finding 必须先复现"铁律同源）；
3. **诚实 N/A**——changeset 中不存在可检测对象时如实披露 `not_applicable`，不得报 0 发现假绿
   （与 C9/C10 覆盖度诚实纪律一致）。

## 2. 目标与非目标

### 目标

- **G1**：review 确定性层新增 **BREAK-1~5 / VULN-1~5 十类断点/漏洞检查**，每条发现以
  编号 category（`BREAK-1`…`VULN-5`）+ 代码位置 + 命中模式名输出，接入 `TwoStageReviewGate`
  Stage 2，用户可见（Markdown 报告 + JSON details）。
- **G2**：诚实适用性披露——changeset 不含任何可检测对象（路由/导航/API 端点定义）时，
  报告明确 `break_vuln: not_applicable` 及原因，不产生假绿；含可检测对象但零发现时，
  报告 `checked: 10 categories, 0 findings`（检查过 ≠ 没检查）。
- **G3**：十类定义固化为**封闭枚举**（编号 + 中文/英文双语句定义 + 检测规则 ID），并新增契约
  条款（C20）锁存在性——分类学本身不允许被静默删改。

### 非目标（明确不做）

- **不做** Playwright 页面采集、BFS 遍历、DB/Redis 内省（上游 SU 能力，场景不同，重依赖不引入）。
- **不做**跨文件语义分析（AST 全量索引 / 类型推断）——确定性层只做**changeset 内 + 显式证据**
  的模式检测；跨文件语义归 LLM 角色判定（review 的 LLM 侧）。
- **不改**四层规则链（C4–C7）、八过滤门（C1–C3）、Stage 1。
- **不做**自动修复——只报发现。
- **不改** `FailureClass`（运行时失败分类学与设计产物分类学职责不重叠）。

## 3. 分类法定义（V1，十类封闭集合）

> 语义适配声明：上游五类面向"页面/路由/业务动线"，本批次适配为"changeset 中的 Web 路由/
> 导航/API 衔接代码"检测。每类给出：编号、定义、检测对象、候选检测规则（细化设计定稿）。
> 检测对象以 Python Web 框架（FastAPI/Flask/Django）为 V1 范围——本仓自身即 FastAPI。

| 编号 | 名称 | 定义 | 检测对象（changeset 内） |
|---|---|---|---|
| BREAK-1 | 入口断裂 | 新增的路由/端点声明无对应可调用处理体（handler/view 函数缺失或为空） | 路由装饰器注册行 vs 同文件/同 changeset 函数定义 |
| BREAK-2 | 出口断裂 | 处理体无任何返回/响应构造路径（全分支 fall-through） | handler 函数体内 return/response 缺失模式 |
| BREAK-3 | 前置条件缺失 | 写操作端点未挂鉴权/守卫装饰器，而同 changeset 同类端点已挂（同组对比） | 路由装饰器行 vs 同文件其他路由的装饰器集合 |
| BREAK-4 | 数据衔接断裂 | handler 调用了 changeset 中不存在且非标准库/已导入的符号（未定义引用的保守子集：同文件可见范围内） | 函数体内调用名 vs 同文件定义/导入集合 |
| BREAK-5 | 业务闭环断裂 | 导航/菜单/链接配置新增的指向目标在 changeset 与既有路由表中不存在 | 导航配置字面量 vs 路由注册集合 |
| VULN-1 | 数据泄漏 | 响应体直接返回 ORM model 对象/原始 query 结果（未过 schema 序列化） | return 语句中的模型直传模式 |
| VULN-2 | 状态不一致 | 多步写操作无事务边界标记（同函数内 ≥2 次写调用且无 commit/transaction 上下文） | 写调用序列模式 |
| VULN-3 | 操作不可达 | changeset 新增端点在导航/客户端调用字面量中零引用（保守子集：同 changeset 内） | 端点路径字符串 vs 引用字符串集合 |
| VULN-4 | 边界缺失 | 写操作端点的 handler 无任何输入校验调用（校验器/类型注解体上不存在） | handler 签名与函数体模式 |
| VULN-5 | 导航不一致 | 同文件路由路径命名风格断裂（如既有 `/api/v1/` 前缀新端点缺失前缀） | 路径字符串集合的前缀聚类 |

规则属性（全部，细化设计验证）：

1. **确定性**——纯 regex/行级解析，零 LLM、零网络、零新依赖；
2. **保守**——只报 changeset 内可证明的模式，宁漏勿误（误报直接摧毁 review 门禁可信度）；
3. **可解释**——每条发现携带 `rule_id`（如 `BV-BREAK1-missing-handler`）+ file:line + 命中片段；
4. **可关闭**——单类可经 review 配置显式禁用（默认全开），禁用行为在 `details` 披露。

**Severity 分级（2026-10-12 用户裁定）**：`critical` = BREAK-1 / BREAK-5 / VULN-1 / VULN-4
（可证明且高危害）；`warning` = BREAK-2 / BREAK-3 / BREAK-4 / VULN-2 / VULN-3 / VULN-5
（regex 检测误报风险较高，观察误报率后再议升级）。

## 6. 测试计划（提纲，细化设计展开）

1. **单元**：十类检查器逐类——正/反/边界用例；枚举封闭性（新增编号需显式登记）。
2. **集成**：`--mode review --changeset` 全链路——发现进 `details` + Markdown；N/A 披露路径；
   禁用单类的披露路径。
3. **E2E（真实靶）**：对本仓 `scripts/dashboard*.py`/`api_server.py` 构造含已知断点的临时
   changeset（探针法，PR 内加删，不入 main）。
4. **模拟真实用户**：CLI `review --preview` 零 LLM 调用承诺不破坏（C11）；`--verbose` 可见
   编号发现明细。
5. **负向门禁**：删除枚举条目或检查器接线 → `check_skill_contract.py` C20 红（反向守护，
   与 G7 教训一致）。
