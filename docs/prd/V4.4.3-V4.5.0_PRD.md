## 1. Background

### 1.1 block/buzz Core Insights

block/buzz (Block Inc. open-source, 1873 commits) is a workspace where humans and AI agents collaborate on the same relay. Its core philosophy — **"Agent as Team Member"** — resonates deeply with DevSquad's original vision: **"upgrade a single AI assistant into a 7-role professional team"**.

Key insights extracted from block/buzz:

1. **Agent Identity Persistence**: Agents have their own secp256k1 keypair + NIP-05 handle + signed event chain. Agent operations are traceable across sessions.
2. **Shared Workspace Persistence**: All participants share one event log; channel history is searchable months later.
3. **Workflow Trace Transparency**: YAML-as-code automation with full trace visibility — users can see what agents decided.
4. **Branch-as-Channel**: Git branch creation auto-creates a channel; CI/review/merge context lives in one place.
5. **Vision-Driven Development**: Complete VISION document system (VISION.md / VISION_AGENT.md / VISION_MESH.md) explaining "why" not just "what".
6. **Protocol-Native Architecture**: ACP harness decouples agent from MCP toolset via protocol composition, not code coupling.

### 1.2 DevSquad Current State Gaps

| Capability | Current State | Gap |
|-----------|---------------|-----|
| Scratchpad persistence | Per-instance JSONL append-write | No cross-session history search |
| Agent identity | Worker uses role_id, no persistent agent ID | Cannot track "same AI" across sessions |
| Workflow trace | Internal WorkflowEngine trace | Not exposed to users in dispatch report |
| Git context | CheckpointManager has state persistence | No semantic link to Git branch/issue/PR |
| Vision docs | SKILL.md is reference manual | No VISION.md explaining "why DevSquad exists" |
| Skill architecture | LLMBackend is protocol-based | Skill registration still uses import, not protocol |

## 3. V4.4.3 — P1: Workspace Persistence Trio + Doc Consistency Gate

### 3.1 P1-1: Scratchpad Cross-Session Persistence

**Problem**: Scratchpad persists to JSONL per-instance, but dispatch end = scratchpad disappears. Users cannot search "what did the architect decide 3 weeks ago".

**Solution**: Add a SQLite-backed `ScratchpadHistoryStore` that:
- Writes every Scratchpad entry to a persistent SQLite DB (keyed by `scratchpad_id` + `entry_id`)
- Provides `search_history(query, since, entry_type, role_id, limit)` API for cross-session search
- Does NOT replace in-memory Scratchpad (still the hot path); SQLite is the cold/archive store
- Auto-cleanup: entries older than 90 days are archived (configurable via `.devsquad.yaml`)

**Acceptance Criteria**:
- [ ] `ScratchpadHistoryStore` class in `scripts/collaboration/scratchpad_history_store.py`
- [ ] `search_history()` returns entries across multiple past scratchpad instances
- [ ] Integration: Scratchpad.write() mirrors to history store when `persist_history=True`
- [ ] Config: `.devsquad.yaml` `scratchpad.history_enabled` + `scratchpad.history_retention_days`
- [ ] Anti-ghost: `_call_counter` tracks all public method calls
- [ ] E2E: dispatch twice → search_history finds entries from both sessions

### 3.2 P1-2: AgentIdentity Persistence

**Problem**: Workers execute as `role_id` (e.g. "architect"). Audit log records `user_id` (the human), not the agent. Cannot answer "which AI instance made this decision?".

**Solution**: Introduce `AgentIdentity` model:
- Each Worker instance gets a persistent `agent_id` (format: `agent-{role}-{short_hash}`, e.g. `agent-architect-a1b2c3`)
- `agent_id` is derived from `role_id` + `llm_backend` + `model` hash (same config = same agent_id across sessions)
- `DispatchAuditLogger` records `agent_id` in every audit event (new optional field, backward-compatible)
- `DispatchResult.worker_results` includes `agent_id` per worker
- New API: `DispatchAuditLogger.query_by_agent(agent_id, since, until)` for cross-session agent behavior tracking

**Acceptance Criteria**:
- [ ] `AgentIdentity` class in `scripts/collaboration/agent_identity.py`
- [ ] `agent_id` deterministic: same (role, backend, model) → same agent_id
- [ ] Audit log schema: add `agent_id TEXT` column (nullable for backward compat)
- [ ] `query_by_agent()` returns all audit events for a specific agent
- [ ] Anti-ghost: integrated into dispatch pipeline naturally (Worker construction)
- [ ] E2E: two dispatches with same config → same agent_id in both audit logs

### 3.3 P1-3: Workflow Trace Visualization

**Problem**: WorkflowEngine has internal step tracking, but users only see the final report. They cannot see "how did the agent team decompose and execute this task?".

**Solution**: Add `WorkflowTrace` section to dispatch report:
- `WorkflowEngine` already records step execution; expose this as a structured `WorkflowTrace` object
- `ReportFormatter` renders a "Workflow Trace" section in Markdown report:
  - Task decomposition tree (task → subtasks → assigned roles)
  - Step execution timeline (step name → role → status → duration)
  - Decision points (where ConsensusEngine was invoked)
- Dashboard: new "Workflow Trace" tab showing interactive timeline

**Acceptance Criteria**:
- [ ] `WorkflowTrace` dataclass in `scripts/collaboration/models_dispatch.py`
- [ ] `WorkflowEngine` populates WorkflowTrace during execution
- [ ] `ReportFormatter` renders "## Workflow Trace" section in Markdown
- [ ] Dashboard: `workflow_trace_views.py` new tab
- [ ] Anti-ghost: trace populated for every dispatch (not optional)
- [ ] E2E: dispatch → report contains Workflow Trace section with ≥1 step

### 4.2 P2-2: Branch-as-Context (Git Context Injection)

**Problem**: dispatch() is Git-unaware. Workers don't know "we're working on branch X" or "this relates to issue Y". block/buzz maps branches to channels for context aggregation.

**Solution**: Add optional Git context injection to dispatch:
- New param: `dispatch(task, git_context=GitContext(branch, recent_issues, open_prs))`
- `GitContext` auto-detected via `git` CLI when `git_context="auto"` (current branch + recent commits)
- Git context injected into Coordinator prompt + Scratchpad as a DECISION entry
- Workers can reference "current branch" / "related issues" in their analysis

**Acceptance Criteria**:
- [ ] `GitContext` dataclass in `scripts/collaboration/models_dispatch.py`
- [ ] `GitContext.auto_detect()` uses `git branch --show-current` + `git log --oneline -5`
- [ ] Coordinator prompt includes Git context section when provided
- [ ] Scratchpad receives a DECISION entry "Git Context: branch=X, recent=..."
- [ ] Anti-ghost: git_context=None (default) preserves existing behavior (backward compat)
- [ ] E2E: dispatch with git_context → report mentions current branch

## 5. V4.5.0 — P3: Skill Protocol-Native Refactor + Performance Baseline

### 5.1 P3-1: Skill Protocol-Native Architecture

**Problem**: DevSquad's `LLMBackend` is protocol-based (Mock/OpenAI/Anthropic switchable), but Skill registration/discovery still uses Python import. Not fully protocol-native — cannot "swap skill layer without touching agent core".

**Solution**: Refactor Skill layer to protocol-native (inspired by block/buzz ACP harness):
- Define `SkillProvider` Protocol in `protocols.py` (register/discover/invoke/instantiate)
- `SkillRegistry` becomes a protocol consumer, not a concrete implementation
- Skills can be registered via: (a) built-in Python import (current), (b) MCP tool bridge, (c) plugin hot-loader
- Agent core (Worker/Coordinator) only knows `SkillProvider` protocol, never imports concrete skills

**Acceptance Criteria**:
- [ ] `SkillProvider` Protocol in `scripts/collaboration/protocols.py`
- [ ] `BuiltinSkillProvider` (wraps current import-based registration, backward-compatible)
- [ ] `MCPBridgeSkillProvider` (bridges MCP tools as skills, new capability)
- [ ] `SkillRegistry.set_provider(provider)` API for swapping
- [ ] Anti-ghost: all 6 existing sub-skills work unchanged through BuiltinSkillProvider
- [ ] E2E: swap provider → same dispatch result (protocol abstraction verified)
- [ ] Migration guide in `docs/guides/SKILL_PROVIDER_MIGRATION.md`

### 10.1 New Items from External Project Analysis

#### 10.1.1 OutputStyle (from i-have-adhd) — P1

**Source**: ayghri/i-have-adhd — 10 rules for ADHD-friendly AI output formatting.

**Problem**: DevSquad 7-Worker reports use "analysis-first" style. 7 paragraphs of analysis before any action item. For action-oriented users (PMs, developers), this is cognitive overload.

**Solution**: Add `output_style` dimension to PromptDials:
- `detailed` (default, current behavior) — full analysis + recommendations
- `action_first` (new) — lead with next action, cap lists at 5, no preamble/recap/closers
- `compact` (existing) — condensed format

**Implementation**:
- `PromptDials`: add `output_style: str = "detailed"` field
- `ReportFormatter`: apply style rules when rendering (action_first: restructure to Action → Details → Next Step)
- Dashboard: dropdown to switch output_style
- CLI: `--output-style action_first`

**Acceptance Criteria**:
- [ ] PromptDials has output_style field with 3 options
- [ ] ReportFormatter action_first mode: first section is "Next Actions" (not "Analysis")
- [ ] action_first mode: lists capped at 5 items (overflow → "and N more")
- [ ] Backward compat: output_style=detailed preserves existing behavior 100%
- [ ] Anti-ghost: _call_counter > 0

#### 10.1.2 SessionResume CLI (from open-code-review) — P1

**Source**: alibaba/open-code-review — `ocr session list` + `--resume <session-id>`.

**Problem**: DevSquad CheckpointManager has SHA256 state persistence + handoff documents, but users cannot resume an interrupted dispatch from CLI. If a dispatch is interrupted (Ctrl+C, crash), the work is lost from user's perspective.

**Solution**: Expose CheckpointManager via CLI:
- `devsquad dispatch --resume <session-id>`: loads checkpoint, continues from last completed phase
- `devsquad sessions list`: lists recent dispatch sessions with status (completed/interrupted)
- `devsquad sessions show <session-id>`: shows checkpoint details

**Implementation**:
- `cli.py`: add `sessions` subcommand + `--resume` flag to `dispatch`
- `CheckpointManager`: add `list_sessions()` + `get_session_status()` (already has load_checkpoint)
- No new storage — reuses existing checkpoint data

**Acceptance Criteria**:
- [ ] `devsquad sessions list` shows recent sessions with status
- [ ] `devsquad dispatch --resume <id>` continues interrupted dispatch
- [ ] Resume fails gracefully if checkpoint corrupted (error message, not crash)
- [ ] Anti-ghost: _call_counter > 0

#### 10.1.3 FileBundler (from open-code-review) — P2 (Review mode only)

**Source**: OCR's smart file bundling — groups related files into review units, each runs as isolated sub-agent.

**Problem**: DevSquad Coordinator decomposes by role (architect sees all, tester writes tests), not by file. Large changesets (20+ files) cause Worker context overload.

**Solution**: Deterministic file bundling for review mode:
- `FileBundler` class: groups files by path prefix + import relationship (deterministic, no LLM)
- Only active when `dispatch(mode="review")` AND file count > 5
- Each bundle assigned to a Worker with isolated context (divide-and-conquer)
- Bundling rules: same directory → same bundle; import chain → same bundle; max 10 files per bundle

**Implementation**:
- `scripts/collaboration/file_bundler.py`: ~150 lines, deterministic grouping
- `Coordinator`: in review mode, call FileBundler before role decomposition
- No LLM involved in bundling (deterministic engineering, per OCR philosophy)

**Acceptance Criteria**:
- [ ] FileBundler groups files by path prefix + import relationship
- [ ] Only active in review mode with >5 files (backward compat: <5 files = no bundling)
- [ ] Max 10 files per bundle (overflow → split)
- [ ] Anti-ghost: _call_counter > 0

### 10.2 Architecture Optimization: SKILL.md Modular Split — P1

**Problem**: SKILL.md is 1216 lines — serves dual purpose (skill description + reference manual). New users must read 1200+ lines to understand DevSquad. This contradicts DevSquad's own "action-first" philosophy.

**Solution**: Split SKILL.md into modular docs:

| File | Content | Target Lines |
|------|---------|-------------|
| `SKILL.md` | Overview + quick start + entry points + links to reference docs | ~300 |
| `docs/reference/MODULE_REFERENCE.md` | Full module table (185+ modules) | ~400 |
| `docs/reference/SUB_SKILLS.md` | 6 sub-skills detailed documentation | ~300 |
| `docs/reference/VERSION_HISTORY.md` | Version history + changelog | ~200 |

**Implementation**:
- Extract module table from SKILL.md → MODULE_REFERENCE.md
- Extract sub-skill details → SUB_SKILLS.md
- Extract version history → VERSION_HISTORY.md
- SKILL.md keeps: description, quick start, 5 entry points, anti-ghost explanation, links to reference docs
- `skill-manifest.yaml`: add `reference_docs` field listing supplementary docs

**Risk Assessment**:
- LOW risk: docs-only change, no code impact
- TRAE skill system: SKILL.md remains the entry point; reference docs are supplementary
- Benefit: new users read SKILL.md in 5 min (was 30+ min)

### 10.3 Architecture Assessment: What NOT to Do in V4.5.0

**Directory reorganization (scripts/collaboration/ → subdirectories)**: 
- 183 .py files in flat directory IS a problem
- BUT: moving files breaks ALL imports across entire codebase + tests
- Regression risk: HIGH (8200+ tests, every test imports from collaboration/)
- **Verdict**: V5.0.0 (major version, breaking changes allowed). V4.5.0 keeps flat structure.

**Sub-skill independence (6 sub-skills → 6 separate TRAE skills)**:
- Against DevSquad's "team" metaphor — users want the full team, not individual roles
- Cross-skill communication would need a new protocol
- **Verdict**: Over-engineering. Not recommended.
