## 1. 背景与目标

### 1.1 评估来源

alibaba/open-code-review（下称 OCR）是阿里内部 AI 代码审查助手开源版。它的核心论断是：

> **纯语言驱动架构对流程缺乏硬约束** —— 让模型自己决定"审哪些文件""审到什么程度""评论挂在哪一行"，等于把工程上必须 100% 正确的事情交给概率系统。

由此暴露的三个失败模式：**覆盖不全**（大变更集选择性跳过文件）、**位置漂移**（报告位置与真实代码对不上）、**质量不稳定**（prompt 微调即波动）。

OCR 的解法是职责切割：**确定性工程负责"绝对不能错"的步骤，Agent 只负责需要推理的部分**。

### 1.2 本 PRD 的目标

对照 OCR 的机制，对 DevSquad 做一次**证据驱动**的现状评估，明确回答两类问题：

- **要改**：已存在的确凿缺陷（违反项目既有纪律、有证据、低争议）
- **可进化**：真实能力缺口，需要设计决策与成本权衡

并产出分波推进方案与对应校验方法。**不追求与 OCR 对齐**——DevSquad 是通用多角色编排器，OCR 是单一用途审查工具，原则可迁移、实现不可复制。

### 1.3 评估方法

1. 只读代码取证（子技能契约、安全门、调度报告、质量度量）
2. 与 OCR 机制逐项对照，只记录**有证据支持**的差异
3. 明确列出"不需要改"的项，避免过度设计
4. **第二轮「通盘核查」**（用户要求"先通盘考虑"）：对每项拟借鉴特性做**全仓调用链检索**，验证其是否真的生效 —— 即检查 `文档有 ≠ 代码有 ≠ 功能可用`。此步发现了 F4（孤儿特性）与 N2（E4 概念错位）
5. **覆盖度核对**：逐项核对已识别特性是否都落进了 P0–P2 波次，缺口单独立项（E7 即由此产生）

DevSquad 已有 `--dry-run`（分析但不执行）可预览执行计划，但**没有解释"为什么这样决策"的路径**：

**风险已实际发生**：项目历史上有多次"决策不可解释导致误诊"的记录（把日志伪影误诊为真实行为、审计 finding 无法复现）。决策理由可查是这类问题的工具级解法。

## 4. 可进化（真实缺口，需设计决策）

### E1【P1】review 子技能补"确定性侧"（最小可行版）

**问题**：`skills/review/handler.py:70-137` 的 `ReviewSkill.review()` 只接受单个 `code` 字符串 + 可选单 `file_path`（manifest `L56-96` 确认：`code` 必填字符串，`file_path` 可选单文件）。**没有**多文件、diff 感知、按文件类型匹配规则、行级锚定。

**关键判断**：这不只是"缺功能"，而是**输入契约在源头排除了确定性**——入口既然是单段 `code` 字符串，"审哪段代码"的决策就必然由调用方（宿主 LLM）承担，"覆盖不全"因此是结构性必然，而非偶发。

> **【N3 修订：范围表述修正】** 原写"review 没有多文件"的依据是 `skills/review/handler.py`（五轴 skill），该结论**仅对 skill 层成立**。**dispatcher 层已有 `mode='review'` + 确定性打包设计**（V4.5.0，源自 OCR，见 F4）。因此 E1 的范围**不是"新建多文件能力"，而是"把既有 review 管线接通（F4）+ 补具名门（本节）"**，避免重复造轮子。
> 同时确认：**具名过滤门在现有代码中完全不存在**——`grep -i 'secret_exclude|unsupported_ext|default_path|too_large|user_exclude|user_include'` 全仓无命中。

**演进内容**：
1. **接通既有 review 管线**（依赖 F4 的修复结论）→ 再扩展输入契约：支持 diff / 多文件（保留单字符串为兼容路径）
2. 具名过滤门 + 具名排除原因：`binary` / `secret_exclude` / `user_exclude` / `user_include` / `unsupported_ext` / `default_path` / `too_large` / `deleted`
3. `secret_exclude` 无条件优先且不可被 `include` 覆盖（安全护栏语义）
4. **免费预览**：`review --preview` 不发起 LLM 调用即可看到"将审哪些文件、排除了什么、为什么"
   - **【R9 修订：由评审意见提升为交付内容】** 默认**只输出汇总计数**，`--verbose` 才展开明细（避免大型仓库输出数百行）
   - **【R9 修订：脱敏为交付要求】** 预览输出涉及敏感路径时**必须脱敏或仅输出计数**（如 `.env.production` 不得明文出现在日志 / CI 输出中）—— 与 `secret_exclude` 同一安全语义

**~~可复用资产~~**（**R1 修订：本判断有误，已作废**）：

> 初版称可复用 `scripts/qa/deterministic_rule_engine.py`。**该判断错误**——此文件 1576 行，已深度耦合 46 条 UI/UX 专用规则、7 设计支柱、`TasteDials` 阈值调节、`PILLAR_TO_CATEGORY` 向后兼容映射；"抽象成通用规则解析层"实为大规模重构，且该文件本身就在项目 Backlog 的"16 个 >800 LOC 待拆文件"名单上，追加职责与技术债方向相反。

**修订后方案**：**新建独立的轻量规则解析模块**（仅 glob 匹配 + 优先级链，约 100 行）。`deterministic_rule_engine.py` **本轮不动**，后续可选接入，不作为本 PRD 目标。

### E2【P1】规则优先级链 + `rules check` 式解释命令

**四层链**（对每个文件路径按序尝试，第一个匹配的模式生效）：

| 优先级 | 来源 | 路径 |
|---|---|---|
| 1（最高） | CLI 参数 | `--rule <path>` |
| 2 | 项目级 | `<repo>/.devsquad/rule.json`（可安全提交） |
| 3 | 用户级 | `~/.devsquad/rule.json` |
| 4（最低） | 内嵌系统默认 | 随包发布的 `system_rules.json` |

**四个必须保留的设计细节**：
- **第一个匹配生效**，不做 merge/override——避免规则叠加产生不可预测行为
- **系统层始终存在** → 永远能解析出某个规则，不存在"无规则"的未定义状态
- 高优先级层文件缺失时**静默跳过**（不是错误）
- **【R2 修订】安全豁免优先于全部用户配置**：安全类规则（敏感路径保护）**永远在 1–3 层之前求值，且不可被任何层覆盖**。新增的项目级 / 用户级 `rule.json` 是可被本地篡改的攻击面——若无此豁免，用户层即可通过 `include` 强制把敏感路径纳入审查（或反向绕过保护），打开绕过路径。此性质与 `InputValidator` / `rbac_fail_closed=True` 的"禁止 fail-open"硬约束同级，**必须写死在代码而非文档**

**解释命令**：`devsquad rules check <path>` 打印生效的**层** + **模式** + **规则正文**。这是 F3 的正面解法。

**依赖顺序**：E2 是 E1 的前置（E1 的规则匹配依赖 E2 的解析层）。

### E3【P2】覆盖度诚实报告（部分结果必须显式标注）

**问题**：`asyncio.gather(return_exceptions=True)`（V4.5.9）保住了并行结果不丢失，但**失败角色的呈现方式未验证**——`report_formatter.py:119-140` 有"错误"模块，但是否逐一标注失败角色、是否在覆盖不全时给出非零退出，需要核实。

**演进内容 + 明确分歧点**：

OCR 在预算超限时停止调度、把跳过文件标为 `failed(budget)`、**部分结果照发并 exit 0**。作为交互工具这合理（用户看得见 `failed` 标记），但**作为 CI 门禁就是假绿**。

**本 PRD 立场**：DevSquad 若用作 CI 门禁，**覆盖不全必须非零退出**。这与 V4.5.19 刚确立的"统计化断言不得掩盖真实回归"是同一原则。E3 的交付物必须包含"覆盖不全 → 非零退出"的显式契约，而非照搬 OCR 的 exit 0。

### E4【P2，N2 修订：定义已改写】代码位置锚定（positioning，**新建**）+ 内容反思（reflection，**复用既有资产**）

> **【N2 修订】原定义有误，已改写。** 原写"`tests/test_anchor_retrospective.py` 表明锚点（anchor）概念已存在但未显式拆分"——**这是误读**。
> [anchor_checker.py:1-14](file:///Users/lin/trae_projects/DevSQuad/scripts/collaboration/anchor_checker.py#L1-L14) 的自我定义是 "V3.7.0 **Goal Alignment** Engine — checks whether current output remains aligned with the **original task goal**"。
> 即：DevSquad 的 `anchor` = **目标漂移检测**；OCR 的 `positioning` = **评论挂在代码哪一行**。**两者不是一回事。**
> 结论：**代码行锚定能力当前完全不存在**（不是"未拆分"）；而 `AnchorChecker` 的目标漂移能力应归入 reflection 侧复用。

**两侧拆解**：

| 侧 | 含义 | 现状 | 本 PRD 处理 |
|---|---|---|---|
| **positioning**（定位） | 结论挂在哪一行代码 | **不存在**；`OutputValidator` 只承担校验闸职责 | **新建**模块：锚点校正，把结论对齐到真实代码行 |
| **reflection**（反思） | 内容对不对 | **已有资产**：`AnchorChecker`（目标漂移）+ `OutputValidator`（校验闸） | **复用/整合**，不重写 |

**演进**：把 positioning 与 reflection 拆成独立于主审查流程的两个模块，提升"报告结论 ↔ 真实代码位置"的一致率与"结论 ↔ 原始目标"的贴合度。

**验收前置（R5 已定）**：positioning 是新建能力，其"一致率提升"**必须先测并落档当前基线数值**（含测量脚本 + 命令输出存档），否则不可验收。

### E5【P1，R3 修订：由 P2 升级】委托模式提升为一等公民（**无需新代码，性价比最高**）

**现状**：`HostLLMBridge` v2 已在技术上解决"使用宿主 LLM"（严格 7 字段 marker fail-closed、路径安全、权限 0700/0600、资源限制，见 V4.5.10），但**产品定位上仍是可选项**。

**演进**：把"宿主 LLM 优先"提为默认路径，并在 SKILL.md 显式声明价值交换。

**为何升为 P1（R3 修订）**：几乎全是定位/文档/默认值调整，不需新代码；而 SKILL.md 已有"Honest Disclosure"章节，补充成本极低。初版将其列为 P2、却把投入最大且自认可能被质疑自评的 E6 放进 W3 波次，属于本 PRD 第 5 节想禁止的过度设计——PM 评审时指出该矛盾，故调整：**E5 升 P1 与 W1 并行推进，E6 降级为 Backlog 提案**。

**【通盘修订：补强】"1 行太薄"——必须写明的工程细节**（否则 E5 会退化成一句口号）：
