## 1. 背景与目标

### 1.1 评估来源

alibaba/open-code-review（下称 OCR）是阿里内部 AI 代码审查助手开源版。它的核心论断是：

> **纯语言驱动架构对流程缺乏硬约束** —— 让模型自己决定"审哪些文件""审到什么程度""评论挂在哪一行"，等于把工程上必须 100% 正确的事情交给概率系统。

由此暴露的三个失败模式：**覆盖不全**（大变更集选择性跳过文件）、**位置漂移**（报告位置与真实代码对不上）、**质量不稳定**（prompt 微调即波动）。

OCR 的解法是职责切割：**确定性工程负责"绝对不能错"的步骤，Agent 只负责需要推理的部分**。

### 1.2 本 PRD 的目标

对照 OCR 的机制，对 DevSquad 做一次**证据驱动**的现状评估，明确回答两类问题：

- **要改**：已存在的确凿缺陷（违反项目既有纪律、有证据、低争议）
- **可进化**：真实能力缺口，需要设计决策与成本权衡

并产出分波推进方案与对应校验方法。**不追求与 OCR 对齐**——DevSquad 是通用多角色编排器，OCR 是单一用途审查工具，原则可迁移、实现不可复制。

### 1.3 评估方法

1. 只读代码取证（子技能契约、安全门、调度报告、质量度量）
2. 与 OCR 机制逐项对照，只记录**有证据支持**的差异
3. 明确列出"不需要改"的项，避免过度设计
4. **第二轮「通盘核查」**（用户要求"先通盘考虑"）：对每项拟借鉴特性做**全仓调用链检索**，验证其是否真的生效 —— 即检查 `文档有 ≠ 代码有 ≠ 功能可用`。此步发现了 F4（孤儿特性）与 N2（E4 概念错位）
5. **覆盖度核对**：逐项核对已识别特性是否都落进了 P0–P2 波次，缺口单独立项（E7 即由此产生）

DevSquad 已有 `--dry-run`（分析但不执行）可预览执行计划，但**没有解释"为什么这样决策"的路径**：

**风险已实际发生**：项目历史上有多次"决策不可解释导致误诊"的记录（把日志伪影误诊为真实行为、审计 finding 无法复现）。决策理由可查是这类问题的工具级解法。

## 4. 可进化（真实缺口，需设计决策）

### E1【P1】review 子技能补"确定性侧"（最小可行版）

**问题**：`skills/review/handler.py:70-137` 的 `ReviewSkill.review()` 只接受单个 `code` 字符串 + 可选单 `file_path`（manifest `L56-96` 确认：`code` 必填字符串，`file_path` 可选单文件）。**没有**多文件、diff 感知、按文件类型匹配规则、行级锚定。

**关键判断**：这不只是"缺功能"，而是**输入契约在源头排除了确定性**——入口既然是单段 `code` 字符串，"审哪段代码"的决策就必然由调用方（宿主 LLM）承担，"覆盖不全"因此是结构性必然，而非偶发。

> **【N3 修订：范围表述修正】** 原写"review 没有多文件"的依据是 `skills/review/handler.py`（五轴 skill），该结论**仅对 skill 层成立**。**dispatcher 层已有 `mode='review'` + 确定性打包设计**（V4.5.0，源自 OCR，见 F4）。因此 E1 的范围**不是"新建多文件能力"，而是"把既有 review 管线接通（F4）+ 补具名门（本节）"**，避免重复造轮子。
> 同时确认：**具名过滤门在现有代码中完全不存在**——`grep -i 'secret_exclude|unsupported_ext|default_path|too_large|user_exclude|user_include'` 全仓无命中。

**演进内容**：
1. **接通既有 review 管线**（依赖 F4 的修复结论）→ 再扩展输入契约：支持 diff / 多文件（保留单字符串为兼容路径）
2. 具名过滤门 + 具名排除原因：`binary` / `secret_exclude` / `user_exclude` / `user_include` / `unsupported_ext` / `default_path` / `too_large` / `deleted`
3. `secret_exclude` 无条件优先且不可被 `include` 覆盖（安全护栏语义）
4. **免费预览**：`review --preview` 不发起 LLM 调用即可看到"将审哪些文件、排除了什么、为什么"
   - **【R9 修订：由评审意见提升为交付内容】** 默认**只输出汇总计数**，`--verbose` 才展开明细（避免大型仓库输出数百行）
   - **【R9 修订：脱敏为交付要求】** 预览输出涉及敏感路径时**必须脱敏或仅输出计数**（如 `.env.production` 不得明文出现在日志 / CI 输出中）—— 与 `secret_exclude` 同一安全语义

**~~可复用资产~~**（**R1 修订：本判断有误，已作废**）：

> 初版称可复用 `scripts/qa/deterministic_rule_engine.py`。**该判断错误**——此文件 1576 行，已深度耦合 46 条 UI/UX 专用规则、7 设计支柱、`TasteDials` 阈值调节、`PILLAR_TO_CATEGORY` 向后兼容映射；"抽象成通用规则解析层"实为大规模重构，且该文件本身就在项目 Backlog 的"16 个 >800 LOC 待拆文件"名单上，追加职责与技术债方向相反。

**修订后方案**：**新建独立的轻量规则解析模块**（仅 glob 匹配 + 优先级链，约 100 行）。`deterministic_rule_engine.py` **本轮不动**，后续可选接入，不作为本 PRD 目标。

### E2【P1】规则优先级链 + `rules check` 式解释命令

**四层链**（对每个文件路径按序尝试，第一个匹配的模式生效）：

| 优先级 | 来源 | 路径 |
|---|---|---|
| 1（最高） | CLI 参数 | `--rule <path>` |
| 2 | 项目级 | `<repo>/.devsquad/rule.json`（可安全提交） |
| 3 | 用户级 | `~/.devsquad/rule.json` |
| 4（最低） | 内嵌系统默认 | 随包发布的 `system_rules.json` |

**四个必须保留的设计细节**：
- **第一个匹配生效**，不做 merge/override——避免规则叠加产生不可预测行为
- **系统层始终存在** → 永远能解析出某个规则，不存在"无规则"的未定义状态
- 高优先级层文件缺失时**静默跳过**（不是错误）
- **【R2 修订】安全豁免优先于全部用户配置**：安全类规则（敏感路径保护）**永远在 1–3 层之前求值，且不可被任何层覆盖**。新增的项目级 / 用户级 `rule.json` 是可被本地篡改的攻击面——若无此豁免，用户层即可通过 `include` 强制把敏感路径纳入审查（或反向绕过保护），打开绕过路径。此性质与 `InputValidator` / `rbac_fail_closed=True` 的"禁止 fail-open"硬约束同级，**必须写死在代码而非文档**

**解释命令**：`devsquad rules check <path>` 打印生效的**层** + **模式** + **规则正文**。这是 F3 的正面解法。

**依赖顺序**：E2 是 E1 的前置（E1 的规则匹配依赖 E2 的解析层）。

### E3【P2】覆盖度诚实报告（部分结果必须显式标注）

**问题**：`asyncio.gather(return_exceptions=True)`（V4.5.9）保住了并行结果不丢失，但**失败角色的呈现方式未验证**——`report_formatter.py:119-140` 有"错误"模块，但是否逐一标注失败角色、是否在覆盖不全时给出非零退出，需要核实。

**演进内容 + 明确分歧点**：

OCR 在预算超限时停止调度、把跳过文件标为 `failed(budget)`、**部分结果照发并 exit 0**。作为交互工具这合理（用户看得见 `failed` 标记），但**作为 CI 门禁就是假绿**。

**本 PRD 立场**：DevSquad 若用作 CI 门禁，**覆盖不全必须非零退出**。这与 V4.5.19 刚确立的"统计化断言不得掩盖真实回归"是同一原则。E3 的交付物必须包含"覆盖不全 → 非零退出"的显式契约，而非照搬 OCR 的 exit 0。

### E4【P2，N2 修订：定义已改写】代码位置锚定（positioning，**新建**）+ 内容反思（reflection，**复用既有资产**）

> **【N2 修订】原定义有误，已改写。** 原写"`tests/test_anchor_retrospective.py` 表明锚点（anchor）概念已存在但未显式拆分"——**这是误读**。
> [anchor_checker.py:1-14](file:///Users/lin/trae_projects/DevSQuad/scripts/collaboration/anchor_checker.py#L1-L14) 的自我定义是 "V3.7.0 **Goal Alignment** Engine — checks whether current output remains aligned with the **original task goal**"。
> 即：DevSquad 的 `anchor` = **目标漂移检测**；OCR 的 `positioning` = **评论挂在代码哪一行**。**两者不是一回事。**
> 结论：**代码行锚定能力当前完全不存在**（不是"未拆分"）；而 `AnchorChecker` 的目标漂移能力应归入 reflection 侧复用。

**两侧拆解**：

| 侧 | 含义 | 现状 | 本 PRD 处理 |
|---|---|---|---|
| **positioning**（定位） | 结论挂在哪一行代码 | **不存在**；`OutputValidator` 只承担校验闸职责 | **新建**模块：锚点校正，把结论对齐到真实代码行 |
| **reflection**（反思） | 内容对不对 | **已有资产**：`AnchorChecker`（目标漂移）+ `OutputValidator`（校验闸） | **复用/整合**，不重写 |

**演进**：把 positioning 与 reflection 拆成独立于主审查流程的两个模块，提升"报告结论 ↔ 真实代码位置"的一致率与"结论 ↔ 原始目标"的贴合度。

**验收前置（R5 已定）**：positioning 是新建能力，其"一致率提升"**必须先测并落档当前基线数值**（含测量脚本 + 命令输出存档），否则不可验收。

### E5【P1，R3 修订：由 P2 升级】委托模式提升为一等公民（**无需新代码，性价比最高**）

**现状**：`HostLLMBridge` v2 已在技术上解决"使用宿主 LLM"（严格 7 字段 marker fail-closed、路径安全、权限 0700/0600、资源限制，见 V4.5.10），但**产品定位上仍是可选项**。

**演进**：把"宿主 LLM 优先"提为默认路径，并在 SKILL.md 显式声明价值交换。

**为何升为 P1（R3 修订）**：几乎全是定位/文档/默认值调整，不需新代码；而 SKILL.md 已有"Honest Disclosure"章节，补充成本极低。初版将其列为 P2、却把投入最大且自认可能被质疑自评的 E6 放进 W3 波次，属于本 PRD 第 5 节想禁止的过度设计——PM 评审时指出该矛盾，故调整：**E5 升 P1 与 W1 并行推进，E6 降级为 Backlog 提案**。

**【通盘修订：补强】"1 行太薄"——必须写明的工程细节**（否则 E5 会退化成一句口号）：

#### (2) P1-1：`test_write_performance` 的绝对时序断言在共享 runner 上不可靠（间歇红）

**证据（`main` 分支夜间 run `35574509278`，真实日志原文）**：


该 run 的 job 级结论：`security` ✗、`test (3.11)` ✗、`test (3.10)`·`test (3.12)` **cancelled**（fail-fast 连带，非自身失败）、其余 ✓。

**间歇性判定（同一测试在 tag run 未复现）**：tag `v4.5.20` 的 run `35687266001` 中 `test (3.10)`/`test (3.11)`/`test (3.12)` **全部 success** → 确认为**间歇性时序抖动**，非确定性缺陷。

**本机基线实测（本次为设定判据而测，真实输出）**：

```
$ ~/.pyenv/versions/3.12.13/bin/python3 /tmp/measure_shs_write.py     # 5 次连续 200 writes
  run 1: 95.5 ms   run 2: 91.0 ms   run 3: 90.4 ms   run 4: 90.3 ms   run 5: 88.4 ms
  sorted: [88.4, 90.3, 90.4, 91.0, 95.5]
  median: 90.4 ms        max: 95.5 ms
```

**性质判定（不得写成"为迁就代码放宽阈值"）**：被测对象是 **200 次 SQLite 写入的墙钟耗时**；[scratchpad_history_store.py:177](../../scripts/collaboration/scratchpad_history_store.py) **每次 `write()` 都 `conn.commit()`**，即 200 次 fsync 语义。本机中位数 **90.4 ms**，而 CI 单次实测 **3823.6 ms** —— **≈42×**。这个差距说明原断言测到的主要是**共享 runner 的 I/O 与调度环境**，而不是写入成本。**结论：缺陷在测试判据（单次绝对测量 + 环境无关假设），不在被测代码** —— 按项目纪律"修的是测试自身的设计缺陷"，且必须在提交信息与本节写明理由。

**既有先例（同源问题，已处置）**：V4.5.19（commit `ae0ea8e`）把 dashboard 面板延迟门禁从"单次 `<100ms`"改为"**5 次中位数 + 150ms 上限**"并加 `flaky` marker 兜底，理由与本次同类。**但本次不得照抄该方案**：本例的环境差异跨度实测约 **42×**（本机 90.4 ms vs CI 3823.6 ms），绝对上限无论取 1500 还是 2500 ms 都仍落在 CI 抖动区间内（会换来第二次 flaky），取到 8000 ms 又等于取消门禁 —— 故本次必须换判据类型，只借用其"中位数 + 失败信息可诊断"的形式。

**处置（P1-1）——判据改为"相对本环境自身的同操作基线"**：

```
control_ms = 同一临时目录下、同表结构、同 commit-per-write 模式下，裸 sqlite3 做 200 次 (INSERT + commit) 的中位数（3 轮）
bench_ms   = 200 次 ScratchpadHistoryStore.write() 的中位数（3 轮）
断言: bench_ms <= max(FLOOR_MS=1000, K=5.0 × control_ms)
失败信息必须同时打印 bench_ms / control_ms / 比值 / 3 轮明细，保持可诊断
```

实现落点：[test_scratchpad_history_store.py](../../tests/unit/test_scratchpad_history_store.py) 的 `test_write_performance` + `_raw_commit_floor_ms()`，常量 `_budget_floor_ms=1000.0` / `_budget_ratio=5.0` / `_budget_runs=3`。**控制量刻意不调用 `ScratchpadHistoryStore`** —— 用被测对象自己做基线会让比值恒等于 1，门禁失效。

设计理由：① **环境无关** —— 比值把 runner 的 I/O 快慢约掉（本机 control≈90ms → 判据仍取 1000 ms 的原始强度；CI 若 control≈3800ms → 上限≈19000ms 但 bench/control≈1.0 仍过）；② **仍能抓真实退化** —— 逐条增删索引、每次写入前先 `SELECT COUNT`（O(n²)）等回归会让**比值**而非绝对耗时爆掉；③ `FLOOR_MS=1000` 保证快机器上不比原断言弱。

**校验方法（三条，缺一不可）**：① 本机定向连跑该测试 ≥5 次全绿；② **受控实验：在子类/monkeypatch 中给 `write()` 注入逐条额外耗时**（源码不动），确认新判据**仍变红**，并在 CI 级慢环境假设下确认**不再假红** —— 证明门禁没被削弱（R11 预防措施第 13 条：门禁必须能复现其要防的失效）；③ 推送后观察 `main` 夜间 CI 的 `test (3.10/3.11/3.12)` 连续若干轮。

#### (13) P0-3【新发现，第九轮】：3 个 mypy 存量错误 + mypy 门禁 `--no-site-packages` 假绿盲区

**用户指令原文（第九轮）**：**「Address and resolve all 3 existing mypy errors in the current codebase as part of this development cycle. Ensure comprehensive fixes that eliminate these specific type checking issues rather than implementing temporary workarounds.」**

**反直觉点（已用实验证伪直觉）**：`i18n.py` 同一行在**两种配置下要求相反** —— 有类型桩时 `st.selectbox` 返回 `int`，索引 `list[Locale]` 得到 `Locale`，故原 `cast(Locale, ...)` 被报 `redundant-cast`；无类型桩时 `st.selectbox` 为 `Any`，`Any` 索引会把结果**重新拓宽回 `Any`**，故去掉 cast 又会触发 `no-any-return`。**显式标注的局部变量同时满足两种配置**，这是唯一无 `type: ignore` 的解法。

**根因修复（非 workaround，未放宽任何检查）**：

| 文件 | 原写法 | 修复后 | 触发规则 |
|---|---|---|---|
| [config_manager.py](file:///Users/lin/trae_projects/DevSQuad/scripts/collaboration/config_manager.py) | `return cast(DevSquadConfig, cls.model_validate(merged))` | `validated: DevSquadConfig = cls.model_validate(merged)` + `return validated`（并移除已无用的 `cast` 导入，避免 ruff F401） | `redundant-cast` |
| [i18n.py](file:///Users/lin/trae_projects/DevSQuad/scripts/dashboard/i18n.py) | `return cast(Locale, options[selected_idx])` | `new_locale: Locale = options[selected_idx]`（显式标注，两种配置下返回类型都诚实） | `redundant-cast` / `no-any-return` |
| [dag_views.py](file:///Users/lin/trae_projects/DevSQuad/scripts/dashboard/dag_views.py) | `st.mermaid(mermaid_text)`（外层 `try/except (AttributeError, RuntimeError)`） | `getattr(st, "mermaid", None)` + `if callable(...)` → 调用（**内层保留 `except RuntimeError`**）/ `else: st.code(...)` | `attr-defined`（且满足 ruff B009） |

**`st.mermaid` 实测（钉住版本 Streamlit 1.57.0）**：`hasattr(st,"mermaid") → False`、`callable(getattr(st,"mermaid",None)) → False`。**该分支在运行时同样不存在** —— 原注释「Streamlit < 1.29 不支持 st.mermaid」的前提**未经核实**，实际行为一直是落到 `st.code`。

**三态行为等价性探针（含独立复核发现的一次自我纠正）**：修复的**第一版**只做了 `getattr` + `callable` 判断，**丢掉了原有的 `except RuntimeError` 回退** —— 独立复核（fresh-eyes 子代理）指出：这已不是"纯类型改动"，若未来 Streamlit 提供**可调用但会抛 `RuntimeError`** 的 `st.mermaid`，旧代码回退 `st.code`、新代码会直接抛出。**已据此把 `except RuntimeError` 补回**。补回后三态探针（真实 `st` 模块打桩，`render_dag_view(None)` 走 Mermaid 分支）：

```
case2 callable-ok:          st.mermaid calls=1  st.code calls=1
case3 raises-RuntimeError:  st.mermaid calls=1  st.code calls=2
```

读法：`st.code` 的**基线调用为 1 次**（"Raw Mermaid" 展开块），故 case1/case3 的 2 次 = 基线 + 1 次回退 → **回退路径确实生效**；case2 的 1 次 = 仅基线 → **`st.mermaid` 可用时不再冗余回退**。三态均与修复前行为一致。

**二、去 flag 的连带发现：门禁绿 ≠ 类型正确（本条的真正主题）**

去掉 flag 后 mypy 立刻报出错误 —— 这**反证**了此前的"mypy 门禁绿"是**被 flag 削掉检查范围**后的绿（与本仓 dispatcher size gate 因前序失败被 `skipped` 属同一类假绿）。三个既有错误已在上一批于**源码层**修复（无 `type: ignore`、无放宽检查、无改门禁），其中 `scripts/dashboard/i18n.py:117` 是**反直觉**的一处：带桩时 `st.selectbox` 返回 `int`，索引 `tuple[Locale, ...]` 得 `Locale`，原 `cast` 被判 `redundant-cast`；不带桩时返回 `Any`，`Any` 索引又**加宽回 `Any`**，去掉 `cast` 反而触发 `no-any-return` —— **两个配置要求相反**，唯一同时满足且不需 `type: ignore` 的修法是显式标注局部变量 `new_locale: Locale = options[selected_idx]`。

**三、numpy 与 `python_version` 的因果链（实测，非推断）**

去 flag 后 mypy 报出**唯一**一个剩余错误：

```
.venv/lib/python3.12/site-packages/numpy/__init__.pyi:737: error: Type statement is only supported in Python 3.12 and greater  [syntax]
```

`numpy 2.5.1` 经 `streamlit` 传递进入 lint 环境的依赖树（`Required-by: pandas, pydeck, streamlit`），其 `__init__.pyi` 使用 **PEP 695 `type` 语句**（第 737 行即 `type _Falsy = L[False, 0] | bool_[L[False]]`），而 mypy 的**目标版本**仍是 3.10 → 解析期即失败。**实测排除两条替代路径**：per-module override `numpy.*` 的 `follow_imports = "skip"` 与 `ignore_errors = True` **均无法抑制解析期错误**（不是类型检查期错误，override 管不到）；`--python-version 3.12` 与 `3.13` 则均 `0 error`。故**目标版本上抬是唯一不改门禁强度的解法**，已请示用户并获准。**已接受的代价**：mypy 不再为项目代码强制 3.10 级语言兼容性（`requires-python` 仍为 `>= 3.10`）；同时已验证 streamlit 桩在新目标下**仍然生效**（`reveal_type(st.selectbox(...))` → `str`），即上抬版本**没有把桩又变回 `Any`** —— 否则等于换了个方式重现假绿。

> **【诚实界定——本条错误的版本边界，勿误读为"CI 曾红"】** 该语法错误的触发条件是**环境里装了 numpy ≥ 2.5**，而 **CI 的 lint job 解析到的是 numpy 2.4.6**（`streamlit-1.64.0` 的 `numpy<3` 约束 + runner 缓存命中）。**逐版本实证**：numpy **2.4.6** 的 `__init__.pyi` 中 PEP 695 `type X = …` 语句数 = **0**（第 730–742 行为 `TypeVar` 写法）；numpy **2.5.1** = **65**。**故 CI 即便保持 3.10 目标也不会因此变红**，该错误是在**开发者环境 / 任何解析到 ≥2.5 的环境**上复现的。**本地观察到的报错真实存在，但不得表述为"CI 的 lint job 曾因此失败"** —— 那是过度归因。上抬目标的价值在于：让**去 flag 后的门禁在所有环境（CI 2.4.6 与开发机 2.5.1）都可用**，而不是去修一次从未发生的 CI 红。

**四、全量改造的设计：控制变量必须 `operation-independent`（一次被证伪又纠正的设计）**

改造入口为新建的 `tests/conftest.py`：

```python
REFERENCE_WORKLOAD_MS_DEV: float = 0.982   # 校准机 2026-09-24, Python 3.12.13

def perf_ceiling_ms(budget_ms: float) -> float:
    return budget_ms * max(1.0, reference_workload_ms() / REFERENCE_WORKLOAD_MS_DEV)
```

控制体是**确定性、零依赖、纯 CPU**的参考负载（4000 次 dict/format/sort 循环），**不触碰任何 DevSquad 模块**。在校准机（本机）上系数恒为 `1.0`，故**每处天花板等于其原始预算** —— 本地强度**零稀释**；在慢机上按该机实测倍率整体放大。各站点的预算数字**逐字保留**（`200.0`、`100.0`、`5000.0`、`0.05` …），**无一处被放宽**。

**关键纠正（受控实验，非代码评审发现）**：第一轮设计对 dep-scan 站点使用了**同代码路径**控制（同 1000 行、同逐行正则）。注入 **13.7× 恒定因子**退化后实测：

```
op(1000 imports) = 556.4 ms    同路径 control = 64.4 ms    ceiling = 2971.4 ms
原 200ms 门禁：556.4 < 200.0  → FAIL（抓红，正确）
同路径门禁：  556.4 < 2971.4 → PASS（漏检，错误）
```

**同代码路径的控制会随回归同比例抬高天花板，使断言在构造上永不失败**。该设计已**全量回退**为 `operation-independent` 控制。这与已批准先例 `tests/unit/test_scratchpad_history_store.py::_raw_commit_floor_ms`（同样回避被测对象）方向一致；该文件**故意保留自有 helper 不迁移**（其控制体为 `max(1000.0, 5.0 × raw-INSERT+commit median)`），属有意为之，非遗漏。
