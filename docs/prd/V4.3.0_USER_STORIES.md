## 3. P0 阶段用户故事 — 安全债清理（必做）

### US-01: pickle Dead Code 删除 + Fallback 安全收紧 (P0-1)

**作为** Security Engineer (Alice)，
**我希望** `cache_interface.py` 中 2 处 pickle dead code 分支被删除、运行时 fallback 安全收紧，
**以便** 收敛 `pickle.loads` 的 RCE 攻击面（OWASP A08:2021），同时不破坏现有 Redis 部署。

**验收标准**:
- [ ] `cache_interface.py` 中 2 处 `elif format == "pickle":` dead code 分支被删除
- [ ] `format="pickle"` 调用抛出 `ValueError`（`test_serialize_rejects_pickle_format` 通过）
- [ ] Redis URL 无密码时 fallback 默认关闭并抛出明确异常（`require_password=True` 校验）
- [ ] E2E 测试 `test_cache_pickle_migration_journey.py` 验证遗留 pickle 缓存加载/拒绝/迁移路径
- [ ] 一次性 Redis pickle payload 扫描报告产出（无遗留 / 有遗留登记）
- [ ] 现有 `tests/test_cache_interface.py` 全部通过，全量回归 0 失败

**优先级**: P0
**估算**: 4 小时
**状态**: ✅ 已完成

### US-02: 技术债持续监控机制 (P0-2)

**我希望** 有一个轻量脚本 `todo_drift_monitor.py` 自动扫描 TODO/FIXME/HACK 标记，对比 `TECH_DEBT.md` 已登记条目，集成到 pre-commit hook 和 CI lint job，
**以便** 新引入的技术债能被自动检测和登记，避免技术债再次积累。

**验收标准**:
- [ ] `scripts/collaboration/todo_drift_monitor.py` 实现 `scan_tech_debt()` / `diff_with_tracker()` / `report_new_debts()` 三个函数
- [ ] 代码行数 <100，复杂度 radon cc < D

- [ ] `tests/test_todo_drift_monitor.py` 约 15 测试，覆盖扫描 / diff / 报告 / 大小写不敏感 / 扩展标记集

## 4. P1 阶段用户故事 — 上游精细化升级（重要）

### US-03: Ponytail lite/full 双模式 + DebtCollector + RequirementTracer (P1-1)

**作为** Test Engineer (Carol) 和 UI Designer (Dave)，
**我希望** Ponytail 决策梯支持 `lite`（8 核心红线，适合测试/UI 角色）和 `full`（16 红线，适合开发角色）双模式，并能通过 `PonytailDebtCollector` 扫描 `# ponytail:` 标记、`RequirementTracer` 追踪 `[REQ-XXX]` 标记，
**以便** 测试/UI 角色的 prompt 注入更简洁（减少 token 开销），同时开发者仍享受完整红线保护，并有工具追踪有意简化和需求实现。

**验收标准**:
- [ ] `full` 模式默认输出与 V3.10.0 行为一致（17 现有测试通过）
- [ ] `lite`/`full` 双模式可配置（`quality_control.ponytail_mode: lite|full`，默认 `full`）
- [ ] `ultra` 模式已删除（grep 无残留）
- [ ] 16 条不可简化红线全部覆盖测试（`PONYTAIL_RED_LINES` 6 原始 + 10 项目规则）
- [ ] `ponytail_debt_collector.py` 实现并新增测试覆盖 UPGRADABLE / ROT_RISK 分类
- [ ] `requirement_tracer.py` 实现并新增测试覆盖 `[REQ-XXX]` 解析 + 实现检测
- [ ] `.devsquad.yaml` 配置项 `quality_control.ponytail_mode` 生效
- [ ] mypy 0 errors / ruff 0 errors / radon cc < D

**优先级**: P1
**估算**: 6 小时
**状态**: ✅ 已完成

### US-04: LoopKernel RollbackStrategy + 独立硬上限 (P1-4)

**作为** Developer (Eve)，
**我希望** LoopKernel 在验证失败时能精准回退到正确的阶段（D3 → TEST_VERIFICATION，其余 → DEVELOPMENT），并有独立于 `max_iterations` 的 `rollback_max_iterations` 硬上限（默认 3），
**以便** 避免无限回退循环，同时保留前 N-1 次迭代的产物（`_accumulated_artifacts`），让回退重试能利用先前工作。

**验收标准**:
- [ ] `RollbackStrategy.determine_rollback()` 对 D1-D6 六个失败阶段的回退目标映射 100% 正确
- [ ] 独立 `rollback_max_iterations` 硬上限默认 3，超限自动 STOP_FAILURE
- [ ] 现有 `LoopEngineeringConfig.max_iterations`（默认 50）保持不变
- [ ] `_accumulated_artifacts` 跨迭代传递验证：第 N 次迭代可访问前 N-1 次迭代的产物
- [ ] 现有 `tests/test_loop_engineering.py` 35 测试同步修改后全部通过
- [ ] 新增约 12 测试覆盖回退映射 / 累计上下文 / 独立迭代上限
- [ ] LoopKernel 五步闭环不被破坏，全量回归 0 失败

**优先级**: P1
**估算**: 5 小时
**状态**: ✅ 已完成
