## 1. 背景与来源

### 1.1 调研对象

[tester-army/e2e](https://github.com/tester-army/e2e)（Apache-2.0，TypeScript）是面向 Web/移动端的
AI 端到端测试框架：用自然语言描述目标，agent 驱动应用到达目标，再用确定性断言验证结果。
它解决的核心矛盾——**agent 测试灵活但昂贵、慢、不稳定；确定性测试便宜但死板**——与本仓
"真实 LLM 测试进不了 PR CI"的痛点同构。借鉴的是三个**模式**，不是框架本身。

### 1.2 机制 → 短板映射

| tester-army/e2e 机制 | 本仓现状短板 | 证据 |
|---|---|---|
| **Replay cache**：agent 动作被录制，且只有后续确定性 check 验证通过才保存；下次运行零模型调用回放；应用变更 → miss → agent 接管；失败回放驱逐；`MODEL_UNAVAILABLE` 不驱逐；运行摘要披露 `AI 2 model calls · Cache 4 replayed` | 真实 LLM 测试永远进不了 PR CI：`tests/external/` CI 永不执行；`tests/e2e/test_real_llm_e2e.py` 有 key 走真实后端、失败静默 fallback mock；CI e2e job 每个 PR 真实烧模型额度 | 本 PRD §4 |
| **Verdict 三分类**：每步裁决 passed/failed/blocked，error code 与 exit code 分开；blocked=凭据/环境/预算，failed=产品判定 | 所有失败混为一谈：API 5xx、key 失效、产品回归都表现为测试红或静默 fallback。V4.5.22 时 `test_dispatch_with_openai` 失败花了一整个调试会话（dispatch-success-false）才归因出"测试 bug 而非产品 bug" | 本 PRD §5 |
| **Act/assert 分离 + 独立 judge**：执行模型自由操作；判定模型看受限上下文，可用独立 judge 模型 | `tests/external/` 断言极弱（`isinstance str` / `len>0` / `"def " in result`）——确定性层（C1–C18）管结构，语义质量无判定 | 本 PRD §6 |

### 1.3 关键现状盘点（设计锚点，均已核实）

1. **`LLMCache` 已存在且已接入生产**（`scripts/collaboration/llm_cache.py`，679 行；
   `worker.py:788-820` 按 `(instruction, "backend", model)` get/put，best-effort，TTL 过期）。
   → P1-a 是**扩展它补回放语义**，不是新建缓存模块（Simplicity First）。
2. **CLI 退出码映射点只有两处**：`scripts/cli_dispatch.py:425`（`0 if success else 1`）与
   `scripts/cli_lifecycle.py:338`。
3. **`llm_backend.py` 924 行，贴近 800 门禁**（`check_dispatcher_size.py --baseline`，
   V4.5.24 起该门禁在 PR CI 跑）→ P1-b 的分类逻辑**必须放新模块**，不得往 llm_backend 加行。
4. **`DETERMINISTIC_CONTRACT.md` 的 C9/C10 承诺"incomplete coverage exits non-zero"**——
   P1-b 不得破坏该承诺（两种失败仍非零，只是 1 与 2 之分）。
5. `CIFeedbackAdapter`（`test_ci_feedback_adapter.py`）是**读** CI 结果注入上下文，方向与本 PRD

## 2. 目标与非目标

### 目标

- **G1（P1-a）**：真实 LLM e2e 可以进 PR CI——首次真实调用录制响应，后续 PR 回放近似零成本，
  prompt/代码变更自动失效，回放比例在报告与 JSON 中诚实可见。
- **G2（P1-b）**：dispatch 失败可区分 `product_failed`（产品判定失败）与 `environment_blocked`
  （凭据/网络/配额/超时）——CI 可据此 retry 而不遮蔽产品回归，消灭"external 失败归因会话"这类成本。
- **G3（W2）**：真实 LLM 测试的语义断言升级（judge 分离）；CI 失败时把 `failed_roles`/coverage/
  failure_class 自动贴 PR 评论。

### 非目标（明确不做）

- **不引入** tester-army/e2e 框架本身（TS/Playwright/Web+mobile 引擎）：DevSquad 是 CLI/MCP
  编排器，不是 web app；Dashboard 真浏览器 E2E 已在 backlog（届时 Playwright-Python 即可）。
- **不做 coverage-based test selection**（fork 版功能）：与"测试找 bug"哲学冲突，选择性跑 = 假绿
  温床；全量 CI 约 15 分钟可接受。
- **不改变** MockBackend 路径的任何行为（生产默认 `off`，零变化）。
- **不缓存** host 委托路径（host LLM 由宿主 Agent 持有，DevSquad 侧无从录制）。

## 4. W1 P1-a：LLM 交互回放缓存

### 4.1 现状与差距

`LLMCache` 现有能力：`(instruction, "backend", model)` 精确键、TTL 过期、内存/磁盘/Redis 多层、
best-effort 读写（异常静默吞掉）。**差距**（对照 replay 语义）：

| # | 差距 | 后果 |
|---|---|---|
| D1 | 键用原始 instruction 字符串，**无版本分量** | prompt 模板代码变更不会失效缓存 → 回放旧响应 = 假绿温床 |
| D2 | TTL 过期 | 测试路径需要确定性：要么命中回放，要么真实调用，不允许"悄悄过期后真调"造成的不可预期 |
| D3 | 无模式控制（永远 read-write） | 无法实现"CI 只读回放" |
| D4 | 无命中统计与披露 | 回放比例不可见——违反"门禁可信度"教训 |
| D5 | 写入无验证门 | tester-army 规则"验证过才保存"在本仓的等价物未定义 |

### 4.2 设计

**新模块 `scripts/collaboration/llm_replay_policy.py`（约 130 行，纯函数，单测友好）**：

> 实施期发现（2026-10-12）：`PromptAssembler.assemble` 的指令内嵌 `Task ID: task-XXX`
> （每次 dispatch 唯一），原始指令直接构键则回放永不命中——这正是 tester-army 用
> `unique()` 包装时间戳/随机邮箱解决的问题。因此 `build_replay_key` 对指令做
> **volatile-metadata 归一化**：剔除 `Task ID:` 行后再散列。归一化只作用于回放键
> （旧缓存键路径零改动）；若未来 prompt 引入其他 per-dispatch 元数据（时间戳等），
> 须同步扩充归一化规则。

```python
class ReplayMode(StrEnum):
    OFF = "off"              # 默认。生产行为零变化
    READ = "read"            # 只读回放（CI 第二跑）
    READ_WRITE = "read-write"  # 首跑录制

def resolve_replay_mode(explicit: ReplayMode | str | None) -> ReplayMode:
    """优先级：显式参数 > env DEVSQUAD_LLM_REPLAY_CACHE > 默认 off。非法值 fail-closed raise。"""

def build_replay_key(instruction: str, backend: str, model: str, *,
                     system: str | None = None, params: dict | None = None) -> str:
    """键 v2：sha256(规范化 instruction + system + 排序后 params + backend + model
    + __version__ + PROMPT_TEMPLATE_VERSION)。
    PROMPT_TEMPLATE_VERSION 常量随 prompt 模板变更手动递增（带注释约定）。
    任何 prompt 代码变更必然 miss —— tester-army '应用变了' 的等价物。"""

def classify_for_write(outcome: str) -> bool:
    """outcome ∈ {'verified','unverified','model_unavailable','product_failed'}。
    仅 'verified' 允许写入；'model_unavailable' 不驱逐既有条目（tester-army 语义）。"""
```

**`llm_cache.py` 扩展（约 +60 行，总量 ~740，仍低于 800 门禁）**：

- `get/set` 增加可选 `mode` 与 `key` 直传（跳过内部散列，用 v2 键）。
- replay 模式下：TTL 视为 ∞（`ttl=None` 语义），写删除策略由 policy 决定。
- 新增 `stats()` → `{"hits": int, "misses": int, "writes": int, "mode": str}`。

**Worker 接线（`worker.py` `_cache_get/_cache_put`，行为仅在 replay 模式非 off 时变化）**：

- off：走现路径，零变化。
- read/read-write：用 `build_replay_key` 构键；`_cache_put` 仅在本次 dispatch 最终成功
  （verified）时写入——dispatch 结束时由 assembler 回调统一结算（见下）。

**写入验证门（D5 的落地方式，实施期设计简化 2026-10-12）**：
原设计的"per-dispatch 待定区 + assembler 结算提交/回滚"存在并发正确性问题——并发 dispatch
共享待定区会互相误驱逐（`test_concurrent_dispatch_stability` 是既有场景），且 run_in_executor
不传播 contextvars，per-dispatch 归属需要侵入式管线改造。简化为**双门语义，等价达成
"验证过才保存"**：

1. **worker 级（既有，保持）**：`_cache_put` 仅在 backend 调用成功返回后执行
   （异常路径不写入——`worker.py` 现行为，零改动）；
2. **CI 级（新增，真正的回放消费者）**：`actions/cache` 的 post 步骤仅在 e2e job 成功时
   保存缓存目录——失败的 dispatch 产物不会进入下一次 PR 的回放源。

本地 read-write 模式下，失败 dispatch 的写入会留在磁盘（与今日 LLMCache 的无条件 best-effort
写入行为一致，**非回归**）；这些条目在下次真实调用同键时被自然覆盖，且不影响 CI 回放源。
tester-army 的"失败回放驱逐"由 CI 层等价实现：中毒条目只有让 job 通过才能存活——
通过即验证。

**诚实披露（D4）**：

- `result.details["replay_cache"] = {"hits": ..., "misses": ..., "writes": ..., "mode": ...}`；
- Markdown 报告末尾一行：`Replay cache: 3 replayed · 1 live (mode=read)`；
- CLI JSON 同步该字段。

**CI 接线（`test.yml` e2e job，约 +12 行）**：

```yaml
      - uses: actions/cache@<SHA> # 复用 #19 的 SHA pin 纪律
        with:
          path: ~/.devsquad/llm_replay_cache
          key: llm-replay-${{ runner.os }}-${{ hashFiles('scripts/collaboration/**/*.py') }}-v${{ vars.DS_PROMPT_TEMPLATE_VERSION || '1' }}
      - name: Run E2E tests ...
        env:
          DEVSQUAD_LLM_REPLAY_CACHE: ${{ secrets.DEVSQUAD_OPENAI_API_KEY && 'read-write' || 'off' }}
      # job 成功才保存缓存 = '验证过才保存' 的 CI 等价物（actions/cache 默认 post 步骤行为）
```

效果：无 prompt 变更的普通 PR → 全量命中 → 零模型调用、秒级真实链路验证；
prompt/代码变更 → 键 miss → 真实调用重建录制（该 PR 的 e2e job 真实消耗一次，
恰好就是"该变更最需要真实验证"的时刻）。

### 4.3 边界（如实声明）

- MockBackend 不进缓存（mock 本身确定性，缓存是无意义的间接层）。
- `tests/external/` 的直接 backend 单测不接入本机制（它们测的就是 backend 本身）。
- 受益面 = `tests/e2e/test_real_llm_e2e.py` 及 CI e2e job 的真实后端路径。
- LLM 输出本身非确定性——回放缓存的意义正是**冻结一个被验证过的响应**，
  这是有意为之，不是缺陷；披露字段让使用者知道冻结比例。

## 5. W1 P1-b：失败分类学（failure taxonomy）

### 5.1 分类法

```python
class FailureClass(StrEnum):
    NONE = "none"                        # success=True
    PRODUCT_FAILED = "product_failed"    # 产品判定失败
    ENVIRONMENT_BLOCKED = "environment_blocked"  # 环境/凭据/配额/超时
```

判定规则（新模块 `scripts/collaboration/failure_taxonomy.py`，约 90 行）：

| 类别 | 判定 |
|---|---|
| `environment_blocked` | `openai.APIConnectionError`、`openai.APITimeoutError`、`APIStatusError`（401/403/407/429/5xx）、backend 显式不可用（key 缺失/链路全部不可用）、host 桥 `ENVIRONMENT_UNAVAILABLE` 类 |
| `product_failed` | 其余一切：schema 违规、空 content（fail-closed）、coverage 不完整（C9/C10）、consensus 拒绝、worker 异常 |

### 5.2 接线（不改 `llm_backend.py`）

- worker 捕获 backend 异常时在 error dict 记录异常类型名（`error["exception"]`，一行）；
- assembler（`dispatch_result_assembler.py`）结算时：errors 中任一 `environment_blocked` 类异常
  **且** coverage 缺失由该异常导致 → `failure_class = environment_blocked`，否则
  `product_failed`；输出进 `details["failure_class"]` 与 Markdown/JSON。
- 明确判定顺序：coverage 不完整但 failed_roles 里有 blocked 异常 → blocked
  （环境是因，coverage 缺失是果）；consensus 拒绝等纯产品判定 → product_failed。

### 5.3 退出码扩展（向后兼容论证）

`cli_dispatch.py:425` 与 `cli_lifecycle.py:338`：

```
0 = success
1 = product_failed（现行为，不变）
2 = environment_blocked（新增）
```

- 所有以 `!= 0` 判定的既有调用方（含 CI `--cov-fail-under` 类 strict 检查）**行为不变**；
- C9/C10 承诺"incomplete coverage exits non-zero"**保持**（1 与 2 都非零）；
- 新语义只做细分：CI 可对 exit 2 走 retry，对 exit 1 立即红。
- REST/MCP 路径同步输出 `failure_class` 字段（退出码仅 CLI 语义）。

### 5.4 契约影响（门禁同步，按 E7 惯例授权）

`DETERMINISTIC_CONTRACT.md` 新增 **C19（failure taxonomy）**：
"dispatch 失败必须携带 failure_class；environment_blocked 与 product_failed 在 CLI 上
以退出码 2/1 区分"。`check_skill_contract.py` 同步增加 C19 的 presence 检查 +
`tests/unit/test_check_skill_contract.py` 对应负向测试。**本 PRD 即 C19 的授权文档**。

### 5.5 顺带修正：real_llm_e2e 的静默 fallback

`tests/e2e/test_real_llm_e2e.py` 现行为"真实后端失败 → fallback mock"正是 P1-b 要消灭的
混淆实例。修正为三段断言：mock 路径必跑；真实路径有 key 时——product_failed 才算测试失败，
environment_blocked 标记 blocked 并显式输出（不再静默降级为 mock 假绿）。

## 7. 测试计划（含 e2e 模拟真实用户，按测试纪律）

### 7.1 单元

- `tests/unit/test_llm_replay_policy.py`：键稳定性（同输入同键）、参数敏感（system/params/model/
  backend/版本任一变化 → 键变）、模式解析优先级（显式 > env > off）、非法 env fail-closed、
  READ 不写 / READ_WRITE 写 / OFF 路径零变化。（注：§4.2 草案中的 `classify_for_write` 随
  双门简化一并取消——无调用方的函数按反幽灵原则不实现。）
- `tests/test_failure_taxonomy.py`：异常映射表（逐异常类型 → 期望类别）、coverage+blocked
  判定顺序、NONE 路径。

### 7.2 集成

- replay read-write → read 两段式：同进程两连 dispatch，第二跑断言零真实 backend 调用
  （spy 计数）且 `details["replay_cache"]["hits"] >= 1`；
- 验证门语义：backend 异常路径不产生缓存写入（spy 键集合断言，worker 级门）；
  `failure_class` 传播：JSON / Markdown / REST / MCP 四出口一致。

### 7.3 E2E（子进程，模拟真实用户）

- **J1 回放旅程**：子进程 CLI dispatch（真 key，read-write）→ 成功；二次同指令（read）
  → exit 0、报告含 `Replay cache: ... replayed`、耗时显著下降；
- **J2 失效旅程**：修改 PROMPT_TEMPLATE_VERSION 重跑 → miss → 真实调用；
- **J3 blocked 旅程**：注入无效 key → exit **2** + `failure_class=environment_blocked`
  + 缓存无写入；
- **J4 产品失败旅程**：构造 coverage 不完整（blocked 缺席）→ exit **1** + `product_failed`。

### 7.4 门禁与回归

- 全量非 external 回归 + cache 选择集 + 版本门禁（77 → 77+N，C19 加入后）+
  依赖锁/同步门禁 + size 门禁（llm_cache.py 预计 ~740 < 800；新模块 ~120/~90 行）+
  `check_skill_contract` 含 C19。
