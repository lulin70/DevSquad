## 1. 背景与问题

### 1.1 V4.5.8 现状（2 项遗留缺口）

V4.5.8 PRD §1.3 明确推迟 2 项，本版一并解决：

| 项 | 原推迟至 | 本版合并原因 |
|---|---|---|
| `Coordinator._execute_parallel` 默认替换为 `asyncio.gather` | V4.5.9 | 用户决策（2026-08-29）：4.5.9+4.5.10 一并解决 |
| `Worker.execute` 改造为 async（LLM HTTP 切换 AsyncClient） | V4.5.10 | 与 gather 迁移强耦合，分开发布会产生中间态（gather 桥接同步 Worker 的假异步） |

### 1.2 关键痛点

#### P1: 双轨并存，同步默认路径仍是线程池

- `coordinator.py` L718-742 `_execute_parallel` 用 `ThreadPoolExecutor(max_workers=10)` + `as_completed`，无超时、结果按完成序收集
- `async_coordinator.py` L426-515 `_execute_parallel_async` 已实现 `asyncio.gather(return_exceptions=True)` + Semaphore + per-task 超时
- 同一"并行执行"语义存在两套实现，行为差异（完成序 vs 提交序、异常兜底字段）是长期维护负担

#### P2: 异步链路是假异步

- `async_coordinator.py` L58-99 `AsyncWorkerWrapper` 通过 `loop.run_in_executor(None, worker.execute, task)` 桥接——Worker 本体仍同步，线程阻塞未消除
- `async_llm_backend.py` 已有 `AsyncOpenAIBackend`（AsyncOpenAI SDK，httpx.AsyncClient 内核）/`AsyncAnthropicBackend`，但 Worker 无 `aexecute` 入口，async 后端在 Worker 链路中无人调用

#### P2: LLM 并发受制于线程池上限

- 10 线程硬上限：并发 >10 时排队；线程切换开销在高并发下放大延迟
- gather + Semaphore 语义下并发上限可配置且无线程开销

### 1.3 不做项（明确 out-of-scope）

| 项 | 推迟到 | 原因 |
|---|---|---|
| `BatchMode.SEQUENTIAL` 串行路径异步化 | 不做 | 串行无并发收益，保持 sync |
| `redis_cache.py`/`llm_cache.py` 单线程后台池改造 | 不做 | 与 worker 执行无关（后台落盘），改造无收益 |
| `HostBridgeBackend`（文件协议）异步化 | 不做 | 文件轮询等待，无线程压力；由 `run_in_executor` 桥接即可 |
| `AsyncFallbackBackend`/`AsyncLLMBackendFactory` 重写 | 不做 | async_llm_backend.py 已完备，直接复用 |
| `_RISK_STORE` SQLite 化 | V4.5.9+ 顺延 | JSON 文件足以覆盖 ≤10000 条目（维持 V4.5.8 决策） |
| `warmup_manager.py` 预热线程池 | 不做 | 独立关注点，避免范围膨胀 |

## 2. 目标与验收标准

### 2.1 P0 目标：`Coordinator._execute_parallel` gather 化（核心）

| ID | 验收 | 度量 |
|---|---|---|
| AC-C1 | `_execute_parallel` 内部实现为 `asyncio.gather(..., return_exceptions=True)`，`ThreadPoolExecutor` 派发机制移除 | 代码审查 + 单元测试断言 gather 路径 |
| AC-C2 | 同步 API 签名不变：`dispatch(task) → dispatch(task)`，调用方零改动 | 现有 56 个 core 测试不修改全部通过 |
| AC-C3 | 单 Worker 失败不丢失其余结果（`return_exceptions=True` 语义），失败项产出 `WorkerResult(success=False, worker_id="unknown", error=...)` 与旧行为一致 | 容错单元测试 ≥4 例 |
| AC-C4 | sync bridge 语义：无 running loop 时安全进入 gather；有 running loop 时 raise informative error（L-V457-002 模式） | 2 个 bridge 测试 |
| AC-C5 | 并发上限经 `asyncio.Semaphore(max_concurrency)` 控制，默认保留 10 | 并发计数测试 |
| AC-C6 | 线程桥接仅存在于 sync Worker 边界：Worker 内部 async 后端原生 await，sync 后端（Mock/HostBridge）经 `run_in_executor` | 后端类型 × 执行路径矩阵测试 |

### 2.2 P0 目标：Worker 原生异步（核心）

| ID | 验收 | 度量 |
|---|---|---|
| AC-W1 | `Worker` 新增 `async def aexecute(task)`，与 `execute` 共享上下文构建/Scratchpad 写入/ArtifactStore 持久化逻辑（单一实现，非复制粘贴） | 代码审查 + 行为一致性测试 |
| AC-W2 | `Worker.aexecute` 对 async 后端（实现 `AsyncLLMBackendInterface`）原生 `await backend.agenerate(instruction)`，不经线程 | 路径断言测试（无 `run_in_executor` 调用） |
| AC-W3 | `Worker.aexecute` 对 sync 后端 fallback：`await loop.run_in_executor(None, self.execute, task)`，行为与旧版逐字节一致 | Mock 后端回归测试 |
| AC-W4 | `AsyncWorkerWrapper` 升级：Worker 有 `aexecute` 时原生调用（消除线程桥），否则 fallback 旧桥接 | wrapper 单元测试 ≥3 例 |

## 3. 范围与子任务

### 3.1 Wave 1：gather 化核心（约 20 测试）

- `coordinator.py`: `_execute_parallel` 重写为 sync bridge + 内部 `asyncio.run(_aexecute_parallel(batch))`；移除 `self._executor` 派发（保留属性过渡或删除——设计阶段定）
- `async_coordinator.py`: 提取 gather 核为共享实现（Coordinator 与 AsyncCoordinator 单一来源，禁止两份 gather 代码）
- 容错矩阵：单失败/全失败/异常类型穿透/BaseException 防御

### 3.2 Wave 2：Worker 异步化（约 25 测试）

- `worker.py`: 新增 `aexecute` + `_ado_work`；async 后端检测（duck-type `agenerate`）
- `async_coordinator.py`: `AsyncWorkerWrapper` 原生路径升级
- `async_llm_backend.py`: 确认 `agenerate` 接口覆盖（不改或仅微调）
- E2E：真异步全链路 + 双路径用户旅程

### 3.3 Wave 3：验证与迁移影响清理（约 15 测试/更新）

- `test_performance_benchmarks.py`: `test_thread_pool_reuse` 按新契约改写（断言 gather 路径并发稳定性）
- 压力测试：50 并发 × {AsyncOpenAI, Mock} × {sync bridge, native async}
- 回归护栏：核心 56 测试零修改通过（AC-C2 硬门槛）

### 3.4 不在本版范围

- SEQUENTIAL 路径异步化
- 缓存后台线程池改造
- SQLite risk store
- LLM HTTP 库从 SDK 换裸 httpx（AsyncOpenAI SDK 内核即 httpx.AsyncClient，满足"httpx.AsyncClient"验收实质）
