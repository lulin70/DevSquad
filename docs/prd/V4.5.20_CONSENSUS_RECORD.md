## 第一轮：角色详细意见

- F3 从"要改"降为"可进化"，或明确标注为"分类边界情形"

### 🔒 Security (8.5/10)

**亮点**:
- ✅ E1 明确要求 `secret_exclude` 无条件优先且不可被 `include` 覆盖，语义正确
- ✅ 第 5 节确认现有安全门已 fail-closed（`InputValidator.validate_task()` 返回 `valid=False`；`rbac_fail_closed=True` 注释"禁止 fail-open"），不盲目改
- ✅ 未照搬 OCR 的做法，而是在对照表中单列"已达标，不改"

**担忧**:
- ⚠️ **E2 新增的项目级 / 用户级规则文件是全新攻击面**。`~/.devsquad/rule.json` 与 `<repo>/.devsquad/rule.json` 可被本地篡改；若优先级链允许用户层覆盖安全相关规则（如把敏感路径加入 `include` 以强制审查），将打开绕过路径。PRD 的 E2 只描述了优先级链，**未写死安全豁免规则**
- ⚠️ E1 的 `--preview` 会打印"将审哪些文件、排除了什么"——预览输出可能泄露敏感路径名（如 `.env.production`）到日志/CI 输出

**建议**:
- **R2（强制）**：E2 优先级链必须显式写死"**安全类规则永远在全部用户配置之前求值，且不可被任何层覆盖**"，并附负向测试（用户级 `rule.json` 尝试 `include` 敏感路径必须失败）
- `--preview` 输出敏感路径时需脱敏或仅输出计数

### 🧪 Tester (8.0/10)

**亮点**:
- ✅ 每个 Wave 都配了校验方法，不是"做完再说"
- ✅ W0-2 要求门禁可被负向测试证伪——这是门禁有效性的唯一判据
- ✅ W1-5 保留向后兼容测试，覆盖了接口扩展的主要风险

**担忧**:
- ⚠️ **W1-4 的断言方式有陷阱**："断言 preview 不触发任何 LLM 调用（mock 计数为 0）"——若只用 backend 层计数，会漏掉内部隐式路径。项目已有明确教训：**monkeypatch 必须打到底层**，patch 上层则其内部埋点不被测到
- ⚠️ **E4 的"锚点一致率提升"不可证**：PRD 未定义基线数值。没有基线就无法判定"提升"，只能事后自证

**建议**:
- **R5（强制）**：W1-4 断言改为 patch 底层 HTTP client；E4 上线前**必须先测出当前基线数值**并记录，否则该项不可验收

**建议**:

## 预防措施

1. **文档先行**：R1–R6 修订必须先落 PRD 文本，再动代码（遵循项目既定顺序：讨论 → 改文档 → 确认 → 改代码）
2. **W0 独立验证**：W0 完成后立即跑门禁负向测试（篡改一个 manifest 验证变红），确认门禁真实有效后再进 CI
3. **E2E 前置**：W1 发布前必须在真实仓库跑完整路径（过滤 → 规则匹配 → 审查 → 报告），模拟真实用户使用
4. **基线优先**：E4 的 positioning 是**新建能力**，实施前必须先测并落档**当前基线数值**（并说明测量方法），否则该 Wave 不可验收；reflection 侧复用 `AnchorChecker` 不得重写
5. **不做无限借鉴**：第 5 节"明确不改"清单为硬边界，任何新增借鉴项须先证明其不违反该清单
6. **先核实再接线（F4 教训）**：任何声称"已接入某管线"的能力，验收必须以**生产调用链**为准（grep 调用方 + 集成测试走管线），不得以"模块存在 + 模块单测通过"为满足
7. **测试名必须与执行路径一致（F4 教训）**：e2e 测试若名为"activates in XX mode"，其内部必须真的经过 XX mode；直接 import 被测模块的测试不得命名/描述为端到端激活 —— **【R11：已门禁化】** 由 `check_module_activation.py::find_unbacked_activation_claims()` 扫描 `tests/e2e/**` 并 fail-closed（PRD §6 W0-6）
8. **文档契约先于代码（E7 决策）**：W1-0 契约未写定前不启动 W1-1~W1-7 的实现，避免"实现完再补文档"导致二次漂移
9. **证据必须可复现（第三轮教训）**：写入 PRD 的任何 grep / 统计结论必须附**原始命令与输出**并标注取证时间。本轮 F1 的"8 处/10 行"错误证明：只读取证若无复核，会带病进入实施基线 —— **多角色评分不能替代证据复核**
10. **前置项未闭合不得开工（第三轮）**：W0 启动前 D5 必须先定；W2-2 启动前 D4 必须先定；W3 启动前 W3-0 必须先过；D7 若确认自证盲区须在 W0 内闭环
11. **文档承诺不得超前于代码（第三轮，E7 风险）**：契约中"尚未实现"的条款须在 SKILL.md 标注生效版本 —— 否则重演 F4 的"文档有 ≠ 功能可用"
12. **判据必须先于核实定义，且判据本身要能证伪（R11，D7 教训）**：D7 的判据（"门禁运行前读计数应为 0"）本身是**方向正确但不够强**的判据 —— 它只能发现"计数器根本不存在"，无法区分"由生产触发"与"由门禁自触发"。**判据设计时必须反问"该判据能否被被测对象自证满足"**；核实手段优先选**跳过被测对象的分离实验**（如 D7 中"跳过门禁、只跑 dispatch 读 delta"），而非在被测对象内部增加断言
13. **门禁断言必须能复现其要防的失效（R11）**：任何门禁上线前，必须显式构造"**该门禁本应防住的那次真实失效**"并确认门禁变红（D7 中即"强制 `changeset=None` 复现 F4"）。只有负向篡改测试（伪造值）不够 —— 伪造值测试证明门禁**读得懂**，复现真实失效才证明门禁**抓得住**
14. **推翻既有裁决必须写明"原裁决基于何种不完整证据"（第八轮，P2-2 教训）**：P2-2 的 report-only 裁决在**未实测"推理 token 能否吃光预算"、未在真实链路复现空内容路径**的情况下作出；本轮先取证（`MT=2048 → reasoning_tokens=2048, content_len=0`）后才改判。**任何改判都要同时留下被推翻裁决的原文与"证据缺口"**（不得只贴新结论，也不得留在同一文档里自相矛盾）；改判实现须防"假绿"（本例：抛错不进重试路径 + 成功计数移到检查之后）
