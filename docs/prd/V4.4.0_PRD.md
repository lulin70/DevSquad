## 2. User Stories

### 2.1 Risk Register (P0-1)

**US-R1**: As a project architect, I want to register a risk with probability × impact assessment, so that the team has a persistent record of threats across the 11-phase lifecycle.
**Acceptance**: `RiskRegister.add()` returns a `RiskItem` with stable `id`; `assess()` updates probability/impact; 7 roles can vote on the assessment.

**US-R2**: As a security engineer, I want to choose one of 4 response strategies (avoid / transfer / mitigate / accept) per risk, so that the chosen strategy drives control selection.
**Acceptance**: `mitigate()` records the strategy + owner + mitigation plan; strategy enum is restricted to the 4 PMP strategies.

**US-R3**: As a DevSquad user, I want the Markdown report to contain a "Risk Management" section, so that I can review open risks without inspecting logs.
**Acceptance**: `export_markdown()` produces a section listing open risks sorted by exposure (probability × impact); section appears in the final dispatch report.

### 2.2 Viewpoint Registry (P0-2)

**US-V1**: As an architect, I want each of the 7 roles to be bound to a formal TOGAF viewpoint, so that consensus conflicts can be arbitrated by viewpoint orthogonality.
**Acceptance**: `ViewpointRegistry` defines 7 viewpoints (architect=functional/data, security=threat, tester=quality, coder=implementation, devops=deployment, pm=requirements, ui=interaction); `ConsensusEngine` uses viewpoint orthogonality to break ties.

**US-V2**: As a tester, I want the viewpoint spec injected into my prompt, so that I produce viewpoint-relevant outputs.
**Acceptance**: `PromptAssembler` injects the viewpoint's `concerns` + `model_elements` into the role prompt; integration test asserts the prompt contains the viewpoint section.

**US-V3**: As a PM, I want a consistency check that flags when two roles produce contradictory outputs on the same model element, so that I can escalate the conflict.
**Acceptance**: `check_consistency()` returns a list of `ConsistencyViolation` with the conflicting roles and the shared model element.

### 2.3 Error Budget Tracker (P1-1)

**US-E1**: As a DevOps engineer, I want to calculate the error budget for an SLO target over a rolling window, so that I know how much budget remains.
**Acceptance**: `calculate()` takes `slo_target` + `window_days` + observed error count; returns `ErrorBudget` with `budget_remaining` and `burn_rate`.

**US-E2**: As a release manager, I want the P10 deployment gate to reject new feature deployments when the budget is exhausted, so that reliability is protected.
**Acceptance**: `UnifiedGateEngine` P10 gate queries `ErrorBudgetTracker.status()`; `status == EXHAUSTED` → verdict REJECT with evidence "error budget exhausted".

**US-E3**: As a dashboard user, I want a budget panel showing remaining budget + burn rate, so that I can monitor reliability at a glance.
**Acceptance**: `Dashboard` renders a new "Error Budget" panel with a progress bar for `budget_remaining` and a numeric `burn_rate`.

### 2.4 Gap Analyzer (P1-2)

**US-G1**: As an architect, I want to define the target architecture in P2 and identify gaps from the current state in P3, so that the roadmap is grounded in real gaps.
**Acceptance**: `analyze()` takes `current_state` + `target_state` and returns a list of `Gap` objects with `work_package` + `effort` estimates.

**US-G2**: As a PM, I want gaps prioritized by priority × effort, so that I can sequence the roadmap.
**Acceptance**: `prioritize()` returns gaps sorted by priority (critical/high/medium/low) then by effort (ascending).

**US-G3**: As a coordinator, I want the `LoopScheduler` CONTINUE decision to reflect whether the last loop closed a gap, so that loops stop when the gap is closed.
**Acceptance**: `LoopScheduler` queries `GapAnalyzer.track()`; if gap-closure delta ≤ 0 across the last loop, decision is STOP.

### 2.5 DORA Metrics Collector (P2-1)

**US-D1**: As a DevOps engineer, I want to collect the 4 DORA metrics from git history, so that delivery performance is measured objectively.
**Acceptance**: `collect_from_git()` returns a `DoraMetrics` with `deployment_frequency`, `lead_time`, `change_failure_rate`, `mttr`.

**US-D2**: As a DevOps engineer, I want to collect DORA metrics from dispatch records, so that AI-driven dispatches are also measured.
**Acceptance**: `collect_from_dispatch()` joins dispatch logs with deployment events; returns the same `DoraMetrics` schema.

**US-D3**: As a release manager, I want the P11 gate to trigger an architecture review when the change failure rate exceeds 15%, so that systemic delivery issues are surfaced.
**Acceptance**: `UnifiedGateEngine` P11 gate queries `DoraMetricsCollector.report()`; `change_failure_rate > 0.15` → verdict CONDITIONAL with suggestion "trigger architecture review".

**US-D4**: As a dashboard user, I want a DORA panel showing the 4 metrics, so that I can monitor delivery performance.
**Acceptance**: `Dashboard` renders a new "DORA Metrics" panel with 4 numeric cards.

## 3. Functional Requirements

### 3.1 P0-1: Risk Register

#### 3.1.1 Background
DevSquad's `UnifiedGateEngine` currently has 6 `GateType` values (`PHASE_TRANSITION`, `WORKER_OUTPUT`, `QUALITY_THRESHOLD`, `SECURITY_CHECK`, `COMPLIANCE_CHECK`, `DEBUG_LOOP_READY`). None of them reason about risk probability × impact. PMP risk management defines a Risk Register with 4 response strategies (avoid / transfer / mitigate / accept). V4.4.0 adds this capability.

#### 3.1.2 Goal
Provide a persistent `RiskRegister` that records risks, assesses them via 7-role voting, applies one of 4 strategies, tracks status, and exports a Markdown "Risk Management" section.

#### 3.1.3 Data Model
```python
class ResponseStrategy(Enum):
    AVOID = "avoid"
    TRANSFER = "transfer"
    MITIGATE = "mitigate"
    ACCEPT = "accept"

class RiskStatus(Enum):
    OPEN = "open"
    MITIGATING = "mitigating"
    CLOSED = "closed"

@dataclass
class RiskItem:
    id: str                       # stable unique id
    description: str
    probability: float            # 0.0 - 1.0
    impact: float                 # 0.0 - 1.0
    response_strategy: ResponseStrategy
    owner: str                    # role id
    status: RiskStatus
    category: str                 # e.g. "technical", "schedule", "security"

class RiskRegister:
    def add(self, description: str, probability: float, impact: float,
            category: str, owner: str) -> RiskItem: ...
    def assess(self, risk_id: str, votes: dict[str, tuple[float, float]]) -> RiskItem:
        """7-role voting: {role_id: (probability, impact)} → weighted mean."""
    def mitigate(self, risk_id: str, strategy: ResponseStrategy,
                 owner: str, plan: str) -> RiskItem: ...
    def track(self, risk_id: str, status: RiskStatus) -> RiskItem: ...
    def query(self, status: RiskStatus | None = None,
              category: str | None = None) -> list[RiskItem]: ...
    def export_markdown(self) -> str:
        """Render the 'Risk Management' section, sorted by exposure (p × i)."""
```

#### 3.1.4 API
- `RiskRegister.add(...)` → `RiskItem` (auto-assigns `id`, default `status=OPEN`)
- `RiskRegister.assess(risk_id, votes)` → applies 7-role weighted voting to update `probability`/`impact`
- `RiskRegister.mitigate(risk_id, strategy, owner, plan)` → updates strategy + status to `MITIGATING`
- `RiskRegister.export_markdown()` → string for the report section

#### 3.1.5 Integration Points
- `UnifiedGateEngine`: new `GateType.RISK_CHECK` — at each phase gate, the engine queries open high-exposure risks (exposure = probability × impact ≥ 0.36) and adds them to `evidence_required`
- `WorkflowEngine`: each phase gate invokes `RiskRegister.query(status=OPEN)` and surfaces blocking risks
- `dispatch_hooks.py`: auto-trigger `RiskRegister.assess()` with the 7-role votes after consensus
- `ReportFormatter`: append `RiskRegister.export_markdown()` as the "Risk Management" section

#### 3.1.6 Acceptance Criteria
- AC-R1: `add()` persists a `RiskItem` with a stable `id` (deterministic hash)
- AC-R2: `assess()` with 7-role votes produces a weighted-mean probability/impact (Architect weight 3.0, Security 2.5, PM 2.0, Tester/Coder 1.5, DevOps/UI 1.0)
- AC-R3: `mitigate()` only accepts the 4 PMP strategies (enum enforced)
- AC-R4: `export_markdown()` lists open risks sorted by exposure descending
- AC-R5: `GateType.RISK_CHECK` blocks phase transition when any open risk has exposure ≥ 0.36
- AC-R6: Module-level `_call_counter` increments on every public method call

### 3.2 P0-2: Viewpoint Registry

#### 3.2.1 Background
TOGAF defines Architecture Views & Viewpoints — each viewpoint addresses a stakeholder concern and operates on a set of model elements. DevSquad's 7 roles currently have no formal viewpoint binding, so `ConsensusEngine` arbitration is role-weight only. V4.4.0 adds a structural axis.

#### 3.2.2 Goal
Bind each of the 7 roles to a formal viewpoint, enable `ConsensusEngine` to arbitrate conflicts by viewpoint orthogonality, and inject viewpoint specs into prompts via `PromptAssembler`.

#### 3.2.3 Data Model
```python
@dataclass
class Viewpoint:
    name: str                       # e.g. "threat"
    concerns: list[str]             # what this viewpoint addresses
    model_elements: list[str]       # which model elements it operates on
    stakeholders: list[str]         # who cares about this viewpoint
    role_id: str                    # bound DevSquad role

class ViewpointRegistry:
    def get(self, role_id: str) -> Viewpoint: ...
    def all(self) -> list[Viewpoint]: ...
    def check_consistency(self, outputs: dict[str, str]) -> list[ConsistencyViolation]:
        """Flag contradictions on shared model_elements across roles."""
    def is_orthogonal(self, role_a: str, role_b: str) -> bool:
        """True if the two viewpoints share no concerns."""
```

#### 3.2.4 The 7 Viewpoints
| Role | Viewpoint | Concerns | Model Elements |
|------|-----------|----------|----------------|
| architect | functional + data | structure, data flow | components, entities, relationships |
| security | threat | attack surface, trust boundaries | assets, threats, controls |
| tester | quality | coverage, failure modes | test cases, defects |
| coder | implementation | APIs, algorithms | classes, functions, modules |
| devops | deployment | runtime, infra | pipelines, services, environments |
| pm | requirements | stakeholder needs | user stories, acceptance criteria |
| ui | interaction | UX, accessibility | screens, flows, components |

#### 3.2.5 Integration Points
- `ConsensusEngine`: on a SPLIT outcome, query `ViewpointRegistry.is_orthogonal(role_a, role_b)` — if orthogonal, both outputs are kept (they address different concerns); if not orthogonal, escalate
- `PromptAssembler`: inject `Viewpoint.concerns` + `Viewpoint.model_elements` into the role's prompt section
- `ReportFormatter`: append a "Viewpoint Consistency" subsection listing violations

#### 3.2.6 Acceptance Criteria
- AC-V1: `all()` returns exactly 7 viewpoints, one per role
- AC-V2: `is_orthogonal("architect", "security")` returns True (different concerns); `is_orthogonal("architect", "architect")` returns False
- AC-V3: `check_consistency()` returns a violation when two non-orthogonal roles contradict on a shared model element
- AC-V4: `PromptAssembler` output contains the viewpoint's `concerns` list for the role
- AC-V5: `ConsensusEngine` SPLIT arbitration prefers orthogonal-pair coexistence
- AC-V6: Module-level `_call_counter` increments on every public method call

### 3.3 P1-1: Error Budget Tracker

#### 3.3.1 Background
SRE Error Budget quantifies the allowed unreliability for an SLO target. DevSquad's P10 deployment gate is currently binary (compliance check); adding an error-budget gate makes it quantitative.

#### 3.3.2 Goal
Calculate the error budget for an SLO target, consume budget on incidents, reset per window, and gate P10 deployments when the budget is exhausted.

#### 3.3.3 Data Model
```python
class BudgetStatus(Enum):
    HEALTHY = "healthy"
    BURNING_FAST = "burning_fast"
    EXHAUSTED = "exhausted"

@dataclass
class ErrorBudget:
    slo_target: float               # e.g. 0.999
    window_days: int                # e.g. 30
    budget_remaining: float         # 0.0 - 1.0 of total budget
    burn_rate: float                # consumption rate vs. expected
    status: BudgetStatus

class ErrorBudgetTracker:
    def calculate(self, slo_target: float, window_days: int,
                  observed_errors: int, total_events: int) -> ErrorBudget: ...
    def consume(self, budget_id: str, error_count: int) -> ErrorBudget: ...
    def reset(self, budget_id: str) -> ErrorBudget: ...
    def status(self, budget_id: str) -> BudgetStatus: ...
```

#### 3.3.4 Integration Points
- `UnifiedGateEngine` P10 gate: query `ErrorBudgetTracker.status()`; `EXHAUSTED` → REJECT new feature deployments (bugfixes allowed)
- `Dashboard`: new "Error Budget" panel showing `budget_remaining` progress bar + `burn_rate` + `status` badge
- `dispatch_hooks.py`: auto-consume budget on incidents recorded during dispatch

#### 3.3.5 Acceptance Criteria
- AC-E1: `calculate(0.999, 30, 10, 10000)` returns `budget_remaining` ≈ 0.0 (10 errors vs 10 allowed for 99.9% over 10000 events)
- AC-E2: `status()` returns `EXHAUSTED` when `budget_remaining ≤ 0`
- AC-E3: `status()` returns `BURNING_FAST` when `burn_rate > 2.0` (consuming 2x the expected rate)
- AC-E4: P10 gate REJECTs feature deployments when `status == EXHAUSTED`
- AC-E5: `reset()` restores `budget_remaining` to 1.0 and clears `burn_rate`
- AC-E6: Module-level `_call_counter` increments on every public method call

### 3.4 P1-2: Gap Analyzer

#### 3.4.1 Background
TOGAF Gap Analysis identifies the delta between current and target architecture, then sequences work packages into a roadmap. DevSquad's P2 (target) and P3 (gap) phases currently have no formal tooling.

#### 3.4.2 Goal
Analyze gaps between current and target state, prioritize them, generate a roadmap, and feed the `LoopScheduler` CONTINUE decision.

#### 3.4.3 Data Model
```python
class GapPriority(Enum):
    CRITICAL = "critical"
    HIGH = "high"
    MEDIUM = "medium"
    LOW = "low"

@dataclass
class Gap:
    id: str
    current_state: str
    target_state: str
    work_package: str
    priority: GapPriority
    effort: float                   # person-days

class GapAnalyzer:
    def analyze(self, current_state: dict, target_state: dict) -> list[Gap]: ...
    def prioritize(self, gaps: list[Gap]) -> list[Gap]:
        """Sort by priority (critical→low) then effort (ascending)."""
    def generate_roadmap(self, gaps: list[Gap]) -> str:
        """Render Markdown roadmap with phases."""
    def track(self, gap_id: str, closure_delta: float) -> Gap:
        """Record gap-closure progress; negative delta = regressing."""
```

#### 3.4.4 Integration Points
- P2 phase: `WorkflowEngine` invokes `GapAnalyzer.analyze()` with the target architecture definition
- P3 phase: `WorkflowEngine` invokes `GapAnalyzer.analyze()` with current vs. target, producing the gap list
- `LoopScheduler`: CONTINUE decision queries `GapAnalyzer.track()` — if the gap-closure delta over the last loop ≤ 0, decision is STOP
- `ReportFormatter`: append the gap roadmap as a "Gap Analysis" section

#### 3.4.5 Acceptance Criteria
- AC-G1: `analyze()` returns one `Gap` per missing/changed capability between current and target
- AC-G2: `prioritize()` sorts critical before high before medium before low; ties broken by effort ascending
- AC-G3: `generate_roadmap()` produces a Markdown table with columns: Phase | Gap | Priority | Effort
- AC-G4: `LoopScheduler` STOPs when `track()` delta ≤ 0 across the last loop
- AC-G5: `track()` with negative delta marks the gap as regressing
- AC-G6: Module-level `_call_counter` increments on every public method call

### 3.5 P2-1: DORA Metrics Collector

#### 3.5.1 Background
DORA Metrics (Deployment Frequency, Lead Time for Changes, Change Failure Rate, MTTR) are the industry-standard signals for delivery performance. DevSquad currently has no delivery-performance measurement.

#### 3.5.2 Goal
Collect the 4 DORA metrics from git history and dispatch records, surface them in a Dashboard panel, and gate P11 on change failure rate.

#### 3.5.3 Data Model
```python
@dataclass
class DoraMetrics:
    deployment_frequency: float     # deploys per day
    lead_time: float                # hours from commit to deploy
    change_failure_rate: float      # 0.0 - 1.0
    mttr: float                     # mean time to recover, hours

class DoraMetricsCollector:
    def collect_from_git(self, repo_path: str, window_days: int) -> DoraMetrics: ...
    def collect_from_dispatch(self, dispatch_logs: list[dict],
                              window_days: int) -> DoraMetrics: ...
    def report(self) -> str:
        """Render Markdown DORA report."""
```

#### 3.5.4 Integration Points
- Git history: parse `git log` for deploy commits (conventional commit `feat:` / `fix:` + tag patterns)
- Dispatch records: join `dispatch_audit.py` logs with deployment events
- `Dashboard`: new "DORA Metrics" panel with 4 numeric cards
- `UnifiedGateEngine` P11 gate: query `DoraMetricsCollector.report()`; `change_failure_rate > 0.15` → verdict CONDITIONAL with suggestion "trigger architecture review"

#### 3.5.5 Acceptance Criteria
- AC-D1: `collect_from_git()` returns all 4 metrics from a fixture repo
- AC-D2: `collect_from_dispatch()` returns the same schema from dispatch logs
- AC-D3: `report()` produces a Markdown table with the 4 metrics + an elite/high/medium/low rating per metric
- AC-D4: P11 gate returns CONDITIONAL when `change_failure_rate > 0.15`
- AC-D5: Graceful degradation on parse errors (shallow clone, rebase) — returns zeros with a warning
- AC-D6: Module-level `_call_counter` increments on every public method call
