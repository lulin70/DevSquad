## 2. 架构概述

### 2.1 架构目标（V4.5.2）

真实执行三路径（B Host Bridge → A 直接 API → C Mock）+ 规模分级门禁 + 性能基线。本文聚焦 **P-1**：规模分级与 RoleMatcher 的路由层级。其余（HostBridgeBackend、B/A/C 解析、测试）后续章节待续。

### 2.2 设计原则

- 复用上游 HostLLMBridge 文件协议，零外部依赖；不引入 Runtime 重写 / 分布式编排。
- **向后兼容**：`dispatch()` 公开签名不变；S/M/L 门禁默认开启但判定保守，保底行为不破坏下游 Consumer。
- 反幽灵：规模分级必须接入 dispatch 真实执行路径且报告用户可见。

## 3. P-1 路由层级架构（规模分级 ↔ RoleMatcher ↔ Coordinator）

### 3.1 现状画像（代码级确认）

现有链路 `dispatch()` → `PreDispatchPipeline.execute()` → `match_roles()` → plan → `_execute_workers()`：

```
[dispatcher.py] dispatch(task, roles=None)
    ├─ RBAC → metrics
    └─ PreDispatchPipeline.execute(task, roles, mode)
         ├─ match_roles()  ──调用──> analyze_task_fn (RoleMatcher.analyze_task)
         │                         └──> roles 非空时 resolve_roles(roles, matched)
         ├─ build plan（含 matched_roles / role_ids / mode）
         └─ Coordinator 编排（multi-role 并行 / 共识）
```

- **RoleMatcher**（[role_matcher.py](file:///Users/lin/trae_projects/DevSquad/scripts/collaboration/role_matcher.py)）→ 回答「**谁来执行**」。`analyze_task()` 按关键词+增强推荐返回 `[{role_id, name, reason}]`；`resolve_roles()` 处理用户显式指定。
- **Coordinator / mode**（`auto/parallel/sequential/consensus`）→ 回答「**怎么编排**」。
- 当前**缺失**「**要多大阵仗**」这道路由：无论任务大小，`mode=auto` 默认全角色并行。

### 3.2 三层路由模型

引入「规模分级门禁」为**第一道路由**，明确三层的职责边界与优先级：

```
┌─ 第一道：规模分级 TaskScale（决定编排深度 / 阵仗大小）── 新增 V4.5.2
│    S 单文件/问答   → 单角色直接执行
│    M 单功能        → 三阶段迷你流（设计要点→开发→测试验证）
│    L 新项目/跨模块 → 完整多角色 + 共识（保留现状最强流程）
│
├─ 第二道：角色匹配 RoleMatcher（决定执行者）
│    在 S/M/L 骨架内选择具体角色；
│    S 限 1 个角色；M 限 2–3 个；L 不限（走现有全匹配）
│
└─ 第三道：执行模式 Coordinator/mode（决定并行/顺序/共识）
     受第一道约束：S 退化为单 worker 顺序；M 用轻量迷你流；
     L 用完整 consensus 编排
```

**关键规则**：
1. 规模分级**先于** RoleMatcher（上游实证：规模分级是第一道路由，角色匹配是第二道路由）。
2. 规模分级**输出约束下传**：`TaskScale` 注入 match_roles 的角色数上限，注入 coordinator 的编排模式。
3. **强顺序依赖对抗**：当第二道识别出「强顺序链」（已定义或启发式），M/L 可退化为**单角色链**，禁用多角色并行（上游实证多 Agent 反降 39–70%）。判定来源见 P-3（待续章节）。

### 3.3 规模分级模块设计（TaskScaleGate）

新增模块 `scripts/collaboration/task_scale_gate.py`，作为 `PreDispatchPipeline.execute()` 最前端步骤（在 `match_roles()` 之前）。

```python
class TaskScale:
    level: str  # S | M | L
    signal: str  # 触发信号（explainable）
    max_roles: int  # 角色数上限约束（下传 RoleMatcher）
    orchestrator: str  # auto | mini | consensus 编排模式约束
    single_role: bool  # 强顺序链 → 单角色链
    matched_role_id: str | None  # S 级强制的目标角色


class TaskScaleGate:
    def decide(self, task: str, roles: list[str] | None,
               mode: str, **kwargs) -> TaskScale:
        ...
```

**判定信号优先级（由高到低，停在第一个满足）**：
| 档位 | 判定信号 | max_roles | orchestrator |
|------|---------|-----------|--------------|
| **L** | 用户显式 `--full` / `--project`；或跨 ≥3 模块 / ≥5 文件；或用户要求"完整流程" | 不限 | consensus |
| **M** | 涉及 2 模块或 3–4 文件；或单功能开发+验证 | 2–3 | mini |
| **S** | 单文件 / 纯问答 / 小修复 / 单函数重构 | 1 | auto (单 worker) |
| **保底** | 未命中（不明确） | M 兜底（宁可多验证） | mini |

**显式覆盖**：CLI 提供 `--scale S|M|L`（强制）+ `--all-roles`（L 等价，保留当前全并行出口）。用户未传 roles 时走门禁判定；**传了 roles 时仍走门禁定编排深度，但角色以用户显式为准**（`resolve_roles` 优先于门禁的角色数上限，且 `max_roles` 仅约束自动匹配）。

### 3.4 插入点与代码改动（surgical）

```
PreDispatchPipeline.execute(task, roles, mode, ...)
  ├─ [新增] scale = task_scale_gate.decide(...)   ← 第一道路由
  ├─ match_roles(task, roles, scale=scale)          ← 第二道路由，注入 max_roles
  │      S 且未指定角色 → 强制选 1 个最高分角色
  │      M → top_k(2..3)
  │      L → 现有全匹配
  ├─ plan(role_ids, orchestrator=scale.orchestrator, single_role=scale.single_role)
  └─ _execute_workers(plan, ...)                    ← 第三道路由，按 orchestrator 执行
```

**改动面**（仅 3 个文件 + 1 新模块）：
- 新增 `task_scale_gate.py`（新，含 `_call_counter`）
- `dispatch_pre_steps.py`：`execute()` 首行调 `decide()`，`match_roles()` 增 `scale` 参数与 S/M 角色数上限逻辑
- `dispatcher.py`：`dispatch()` 透传 `--scale` 覆盖参数（`**kwargs`）
- `cli.py`：新增 `--scale/--full/--all-roles` 参数
- 不触碰 `role_matcher.py` 现有接口（S/M 上限在 pre_steps 层应用，保持 RoleMatcher 纯匹配职责）

### 3.5 数据结构与接口

| 数据实体 | 字段 | 类型 | 说明 |
|---------|------|------|------|
| TaskScale | level | str S/M/L | 规模分级结果 |
| TaskScale | max_roles | int | 自动匹配角色数上限（下传） |
| TaskScale | orchestrator | str | auto/mini/consensus 编排约束 |
| TaskScale | single_role | bool | 强顺序链单角色链标志 |
| TaskScale | matched_role_id | str\|None | S 级强制角色 |

**报告可见性（反幽灵）**：DispatchResult 新增 `details["task_scale"]` + 报告章节「规模分级：S/M/L（signal）」，用户可见即反幽灵门禁通过依据。

### 3.6 向后兼容与风险

| 约束/风险 | 处理 |
|----------|------|
| `dispatch()` 公开签名不变 | scale 通过 `**kwargs` 传入，默认 None→门禁判定 |
| 现有用户依赖 `mode=auto` 全并行 | 默认开启门禁（击破小任务门槛是 V4.5.2 价值）；提供 `--all-roles` 显式回到全并行；`--scale` 强制覆盖 |
| 判定保守性 | 保底到 M（宁可多验证）；S 仅单文件/问答明确信号才触发 |
| 误判致功能缺失（新幽灵） | 保守起步 + 反幽灵 E2E 覆盖 S/M/L 三档路由断言 |
| scale 与现有 mode 冲突 | 优先级 scale.orchestrator > mode（mode 未显式指定时才能被覆盖） |

### 3.7 测试要点（配合 P-4 测试方案章节）

- 单测：`decide()` 对 S/M/L/保底/显式覆盖各信号用例；max_roles 下传正确。
- 集成：S 档 dispatch 实际只起 1 个 worker；M 档起 2–3；L 档全角色+共识。
- 反幽灵：任务规模章节在报告中可见；`task_scale_gate` `_call_counter > 0`。

## 4. P-3 强顺序链判定来源

### 4.1 问题背景

上游（TraeMultiAgentSkill v2.8.4 动态工作流路由表）经验：**强顺序依赖、链式推理任务（调试根因分析、数学推导、分步重构）多 Agent 并行反降 39–70%**。PRD §4.2/§7.3 已明确「强顺序链 → 禁用多 Agent、单一角色顺序完成」。P-3 回答**判定来源**——自动化如何决定这是强顺序任务。

### 4.2 判定来源（按优先级，互斥命中即停）

**核心原则：保守、用户优先、可解释、自动兜底不猜。**

```
判定优先级（命中即停）
├─ ① 用户显式 → 唯一可信来源
│   CLI 标记：  --sequential / --no-parallel  → 强制 single_role=True
│   标记：    --sequential  → single_role=True
│   反标记：  --allow-parallel → single_role=False
│
├─ ② 角色显式意图标签 → 次可信来源
│   角色 prompt 内嵌 `sequential_only: true` 字段（角色元数据声明）
│   典型角色：debugger（V4.5.3 Artifacts 落地）、refactor-expert、数学推导类
│   该字段在 ROLE_REGISTRY 中声明（models.py），判定器读
│
├─ ③ 任务信号启发式 → 自动兜底（最后）
│   见下表
│
└─ ④ 默认（无信号）→ single_role=False（允许多 Agent）
       保守兜底，宁可多并行不可漏断；并行一旦反降仅单次性能受损
```

### 4.3 任务信号启发式表（兜底层）

| 信号类别 | 判定关键词 / 模式 | 权重 | 命中阈值 | 备注 |
|---------|------------------|------|---------|------|
| 调试根因 | debug / 根因 / root cause / trace bug / 复现 → 修 | +3 | 累计 ≥3 | 上游明确点名 |
| 数学推导 | prove / 推导 / 数学 / 公式 / 证明 / step-by-step | +3 | ≥3 | |
| 分步重构 | refactor step / 分步 / 分阶段改 / incrementally migrate | +2 | ≥3 | 需配合修改规模 |
| 单文件修改 | ≤1 文件 且无歧义信号 | 默认 | N/A | 已在 S 档层过滤，此处不重复 |
| 模糊大任务 | 「整体重写」「重构整个 X」等宽泛表述 + M/L | +1 | 仅加分 | 偏向单链 |

**反对触发（强反证）：**
| 类别 | 反例 | 单链？ |
|------|------|--------|
| 显式分派 | 「架构师评审 + 安全审查 + 测试设计」 | 否（多角色） |
| 并列枚举 | 「需要 X、Y、Z 三方面意见」 | 否 |
| 共识门 | 用户显式 `--consensus` | 否 |

**反例 > 正例**——命中反对触发即关闭单链（避免误伤）。

### 4.3 模块设计（OrderChainDetector）

新增模块 `scripts/collaboration/order_chain_detector.py`：

```python
class OrderChainDecision:
    single_role: bool            # 最终单链判定
    source: str                  # user / role_meta / heuristic / default
    signal: str                  # 命中的具体信号（explainable）
    score: int                   # 启发式累计分（debug）
    role_id: str | None          # 单链角色（如有强角色绑定）


class OrderChainDetector:
    def detect(self, task: str, roles: list[str] | None,
               mode: str, **kwargs) -> OrderChainDecision: ...
```

判定流程：
1. 读 kwargs → user flags (`sequential=True` / `no_parallel=True`)
2. 读 roles → 查 ROLE_REGISTRY 元数据，任一角色 `sequential_only=True` → 单链 + source=role_meta
3. 启发式扫描 → 信号累计 + 反例否决 → 输出 score/signal
4. 累计分 ≥ 3 且无反例 → single_role=True
5. 默认 false

### 4.4 插入点与代码改动（surgical）

```
PreDispatchPipeline.execute(task, roles, mode, ...)
  ├─ [新增] scale = task_scale_gate.decide(...)              ← §3 第一道
  ├─ [新增] chain = order_chain_detector.detect(...)         ← §4 第二道路由补充
  │      chain.single_role → 注入 scale/single_role
  ├─ match_roles(task, roles, scale=scale, chain=chain)      ← 与 §3 协同
  └─ plan(..., single_role=chain.single_role)
       ↓
  Coordinator：chain.single_role=True → 走单角色链（顺序）
               否 → 走原 parallel/consensus
```

**改动面（仅新增 + 注入，不破坏现有接口）：**
- 新增 `order_chain_detector.py`（含 `_call_counter`）
- `dispatch_pre_steps.py`：`execute()` 在 scale 之后调 `detect()`，`match_roles()` 与 `build_plan()` 增 `chain` 参数
- `role_matcher.py` 不动（职责纯匹配）
- `models.py` ROLE_REGISTRY 增加 `sequential_only: bool` 字段（角色元数据扩 1 字段，向后兼容）

### 4.5 报告可见性（反幽灵）

DispatchResult `details["order_chain"]` 增：
- `single_role: bool`
- `source: str`（user/role_meta/heuristic/default）
- `signal: str`（如 "user --sequential" / "heuristic: debug+trace=4"）
- `score: int`

报告章节「顺序链判定：单链 | 多 Agent（信号）」，**用户可见即反幽灵门禁通过依据**。

### 4.6 向后兼容与边界

| 风险 | 处理 |
|------|------|
| 启发式误判多 Agent 变单链 | 反例否决 + 默认 false；用户显式覆盖强 |
| 现有 `mode=auto/parallel/sequential` 与 single_role 冲突 | 优先级 user flag > chain > mode（mode=sequential 与 single_role=True 同义；mode=parallel + chain.single_role → chain 优先） |
| 角色元数据字段新增 | ROLE_REGISTRY `sequential_only: bool = False` 默认值，向后兼容 |
| 启发式累计分阈值 | 单一阈值（≥3）保守起步，灰度验证后调 |
| 报告章节新增 | 与现有 details["..."] 字段名规范一致，不影响 to_markdown 既有格式 |

### 4.7 与 §3 P-1 的关系

| 层级 | §3 P-1（规模分级） | §4 P-3（顺序链） |
|------|-------------------|------------------|
| 决策位置 | 第一道路由（先） | 第二道路由内补充（在 match_roles 之前） |
| 维度 | 编排深度（阵仗大小） | 编排方式（并行/单链） |
| 输出 | max_roles / orchestrator | single_role |
| 触发 | 任务规模信号 | 顺序依赖信号 |
| 关系 | S 档天然单角色（不需 §4） | M/L 中识别强顺序链时降级 |

二者正交：规模分级决定**多深**，顺序链决定**多并行**。M/L 档 + 强顺序链 = mini 编排但 single_role=True（单角色链式执行）。

### 4.8 测试要点

- 单测：detect() 对 user flag / role_meta / heuristic 累计 / 反例否决 / 默认各用例；score 与 signal 输出。
- 集成：debug 类任务走 single_role；多角色共识任务不被单链化。
- 反幽灵：`order_chain_detector` `_call_counter > 0`；DispatchResult `details["order_chain"]` 章节在 `to_markdown` 输出中可见。

## 5. P-4 宿主 E2E 可执行测试方案

### 5.1 问题与约束

PRD §9.4 要求「Host Bridge 端到端（宿主读 marker→Task→原子回传→脚本接收）模拟真实用户 E2E」是 release 门禁。但**测试门禁里没有真实宿主 LLM**：

- CI / DevSquad 本地：无人值守，没有 `TRAE` / `ClaudeCode` IDE 进程
- 真实 SubAgent 调度需要 LLM 响应 + IDE 进程 + 协议轮询，开发机不可能常驻
- 用户规则 3：发布前必须模拟真实用户 E2E → **不允许跳过（skip）或标记 env-failed 蒙混**

**必须设计可执行模拟宿主集成测试**——既能复现 HostLLMBridge 协议全链路，又能被自动化 CI 跑通。

### 5.2 方案：FakeHostRunner（进程级隔离的可执行模拟宿主）

**核心思路**：HostLLMBridge 是**纯文件协议**——宿主只需「每 5s 读 protocol.marker → 读 request_*.json → 写 response_*.json」。CI 里**用独立子进程模拟宿主行为**，无需真实 IDE/LLM 介入，但完整复现文件协议链路。

```
DevSquad 主进程（dispatch）           FakeHostRunner（独立子进程）
  │                                          │
  ├─ HostLLMBridge.create_request()           │
  │   写 request_{id}.json + protocol.marker  │
  ├─ wait_for_response(id, timeout=600s)      │
  │   每 0.5s 轮询 response_{id}.json         │
  │                                          │ ── 启动 ──> 监控 logs/host_llm_bridge/
  │                                          │     每 0.5s 扫描 marker
  │                                          │     命中：读 request_*.json
  │                                          │     生成响应（确定性模板 或 内嵌 prompt 校验）
  │                                          │     调 write_response() 原子回传
  │                                          │     清 marker
  ├─ 收到 response → 解析 → 出真实结论报告   │
```

### 5.4 平台检测与执行器

`host_llm_bridge.py` 是协议层；执行器 `HostBridgeBackend(LLMBackend)` 在 `llm_backend.py` 中：

```python
class HostBridgeBackend(LLMBackend):
    """B 路径执行器：升级自 TraeBackend passthrough 为真实 request→response 闭环。"""

    def __init__(self, bridge_dir: str | None = None,
                 timeout_seconds: int = 600):
        self.bridge = HostLLMBridge(bridge_dir=bridge_dir)
        self.timeout = timeout_seconds
        self._failures: dict[str, int] = {}  # reason -> count (熔断状态)
        self._disabled = False

    def _detect_platform(self) -> str:
        # 平台检测：host_llm > claude_code > unknown
        if os.environ.get("TRAE_ENV") or os.environ.get("TRAE_AGENT_PATH"):
            return "host_llm"
        if os.environ.get("CLAUDE_CODE_ENV") or os.environ.get("ANTHROPIC_ENV"):
            return "claude_code"
        return "unknown"

    def is_available(self) -> bool:
        # host_llm 平台 + 未被熔断跳过 → 可用
        if self._disabled:
            return False
        return self._detect_platform() != "unknown"

    def generate(self, prompt: str, role_name: str = "", **kwargs) -> str:
        if not self.is_available():
            raise BackendUnavailable("Host Bridge 不可用（未检测到编程 AI 宿主）")
        agent_type = role_name or kwargs.get("agent_type", "general")
        task = kwargs.get("task_description", "")
        context = {"role_name": role_name, **kwargs}
        request_id = self.bridge.create_request(
            agent_type, task, context, prompt, timeout_seconds=self.timeout
        )
        result = self.bridge.wait_for_response(request_id, timeout=self.timeout)
        # 熔断：B 单次失败 + 连续同因 → 跳过 B（本 dispatch 仅走 A/C）
        if not result.get("success"):
            self._record_failure(result.get("error", "unknown"))
        return result.get("output", "")

    def _record_failure(self, reason: str) -> None:
        """连续 2 次同因 → 熔断跳过 B（非 fatal，按 PRD §5.2 修订语义）。"""
        self._failures[reason] = self._failures.get(reason, 0) + 1
        if self._failures[reason] >= 2:
            self._disabled = True
```

`create_backend("host", ...)` / `create_backend("auto", ...)` 解析顺序按 PRD §4.2 B→A→C。

## 6. P-5 性能基线样本策略

### 6.1 目标与基线原则

**目标**：建立可复现、可被 CI 阻塞化的性能基线，**仅快照真实执行路径**，排除超时/熔断/失败样本以免污染 P95/P99。

**三不收原则**（沿用上游 + 用户规则 3）：
- 不收 Mock 替代品作"基线代表"——Mock 不是真实执行；仅在"mock 路径 P95 变化 <10%"门禁时使用
- 不收首次冷启动——首跑含 import / 缓存 / JIT 抖动，与稳态差异 5–10×
- 不收失败/超时样本——600s 超时纳入会拉爆 P99，掩盖真实回归

### 6.2 样本策略矩阵（按执行路径）

| 执行路径 | 样本范围 | 样本数 | 采集触发 | 排除规则 |
|----------|---------|--------|---------|---------|
| **C Mock** | 单角色直接 dispatch 全过程 | 50 次（连续） | release tag + 本地 benchmark 命令 | 排除 KeyboardInterrupt |
| **B Host Bridge**（FakeHostRunner 子进程） | `create_request`→`wait_for_response` 单次 | 50 次 | release tag + 本地 benchmark 命令 | 排除：超时（>10s 视为无效）；marker 损坏重试 >3 次；熔断后样本 |
| **A 直接 API / OpenAI-Anthropic-MOKA** | LLM `generate` 单次（最小 prompt "ping"） | 20 次（避免计费爆炸） | release tag + CI secrets 注入 | 排除：5xx、429 rate limit、网络错误；不收"长 prompt"——只测稳态网络延迟 |
| **A→C 降级链路** | `create_backend("auto")` 解析到 A 后失败的回路 | 10 次 | 仅本地 benchmark | 排除：CI 不跑（成本） |

### 6.3 稳态样本采集协议

**冷启动丢弃**：每条路径前 5 次视为 warm-up，**不纳入基线**。从第 6 次开始采集。

```python

WARMUP_DISCARD = 5
SAMPLE_COUNT = {"mock": 50, "host": 50, "api": 20, "auto_fallback": 10}

def collect_baseline(path: str, backend: LLMBackend) -> PerfSnapshot:
    """采集稳态样本，丢弃 warm-up 与失败样本。"""
    samples = []
    for i in range(SAMPLE_COUNT[path] + WARMUP_DISCARD):
        t0 = time.perf_counter()
        try:
            result = backend.generate(PING_PROMPT, role_name=ROLE, task=...)
            latency_ms = (time.perf_counter() - t0) * 1000
        except Exception as e:
            continue  # 失败样本不收
        if i < WARMUP_DISCARD:
            continue  # 冷启动不收
        if is_excluded(result, path):  # 超时/熔断/损坏
            continue
        samples.append(latency_ms)
    return compute_snapshot(samples, path=path)
```

### 7.5 LLMBackend 接口契约（V4.5.2 扩展）

```python
class LLMBackend(ABC):
    """V4.5.2 扩展：每条路径的 backend 必须声明 path 与 is_available() 语义。"""

    # V4.5.2 新增：路径标识（用于解析、降级、反幽灵、报告）
    path: str  # "B" | "A" | "C"

    @abstractmethod
    def generate(self, prompt: str, **kwargs: Any) -> str: ...

    @abstractmethod
    def is_available(self) -> bool:
        """V4.5.2 语义统一：
        - B：宿主在 + 未被熔断跳过
        - A：api_key 非空 + provider 可达（is_available 探测）
        - C：始终 True
        """

    # V4.5.2 新增：路径探测时的元数据（解释给 dispatcher）
    def capability(self) -> dict:
        """返回执行能力元数据，供 dispatcher 报告使用。"""
        return {"path": self.path}


class HostBridgeBackend(LLMBackend):    # path = "B"
    path = "B"
    def is_available(self) -> bool: ...  # 见 §5.4 已有实现

class OpenAIBackend(LLMBackend):       # path = "A"
    path = "A"
    def is_available(self) -> bool:
        # 新增：探测 provider 可达性（轻量 ping / list models）
        return self._api_key is not None and self._ping_provider()

class AnthropicBackend(LLMBackend):    # path = "A"
    path = "A"
    def is_available(self) -> bool: ...

class MockBackend(LLMBackend):          # path = "C"
```

### 7.7 降级与熔断契约（PRD §5.2）

```python
class FallbackBackend(LLMBackend):
    """V4.5.2 扩展：内置 B/A/C 路径降级 + 同因失败熔断跳过。

    与 V4.5.1 行为差异：
    - V4.5.1：按列表顺序降级，每次失败 cooldown
    - V4.5.2：记录 reason；连续 2 次同因失败 → 跳过该路径（不重试）
    """
    path = "B+A+C"

    def __init__(self, backends: list[LLMBackend], cooldown_seconds: float = 30.0):
        self._backends = backends
        self._cooldown = cooldown_seconds
        self._failures: dict[str, int] = {}     # reason -> 计数
        self._skipped: set[int] = set()          # 已熔断跳过的 backend index

    def is_available(self) -> bool:
        return any(b.is_available() for i, b in enumerate(self._backends) if i not in self._skipped)

    def generate(self, prompt: str, **kwargs: Any) -> str:
        last_err: Exception | None = None
        for i, b in enumerate(self._backends):
            if i in self._skipped:
                continue
            if not b.is_available():
                continue
            try:
                return b.generate(prompt, **kwargs)
            except Exception as e:
                reason = classify_error(e)
                last_err = e
                self._record_failure(i, reason)
                continue  # 不重试，立即试下一个 backend
        raise BackendUnavailable("B/A/C 全部路径不可用") from last_err

    def _record_failure(self, idx: int, reason: str) -> None:
        key = f"{idx}:{reason}"
        self._failures[key] = self._failures.get(key, 0) + 1
        if self._failures[key] >= FUSE_SKIP_AFTER_CONSECUTIVE:
            self._skipped.add(idx)
```

## 8. 安全与部署

### 8.1 安全目标

满足**用户确认的安全约束**（carrymem 决策）：「LLM API Key 在本机内部环境使用 OK，但绝不能暴露在代码、文档、配置文件等推送到 Git 或服务器的位置」。

V4.5.2 涉及的安全面：
- **A 路径**（OpenAI/Anthropic/MOKA）—— 直接 API key
- **B 路径**（Host Bridge）—— 无 key，但有文件协议层安全（路径遍历、原子写入、权限）
- **C 路径**（Mock）—— 无外部依赖，无敏感面
- **CI / Release** —— tag 触发、secrets 注入、产物清理

### 8.2 密钥管理矩阵

| 路径 | 来源 | 存储位置 | gitignore | 落码风险 |
|------|------|---------|-----------|---------|
| **A** OpenAI/Anthropic | 环境变量 | `DEVSQUAD_OPENAI_API_KEY` / `DEVSQUAD_ANTHROPIC_API_KEY` | 第 36 行 `.env` 已覆盖 | 无（环境变量不落码） |
| **A** MOKA | 环境变量 | `MOKA_API_KEY` | 同上 | 同上 |
| **A** 本地开发兜底 | 本地文件 | `~/.config/devsquad/.env`（用户级） | **不在项目内** | 无（不在 repo） |
| **B** Host Bridge | 无 | 不适用 | 无 | 无 |
| **C** Mock | 无 | 不适用 | 无 | 无 |

**读取链**（按优先级，互斥）：
1. 显式 kwargs（`create_backend("openai", api_key=...)`）—— 仅 API/SDK 内部传递
2. 进程环境变量（`os.environ.get(...)`）
3. 用户级 `~/.config/devsquad/.env`（仅本机开发兜底，不进项目目录）
4. **不读**项目内 `.env`（避免误追踪）

**禁止**：
- ❌ 默认值中包含 key 字面量
- ❌ 错误信息中含 key 前缀/后缀（如 `key[-4:]`）
- ❌ 日志/异常链中含 `Authorization` header / `api_key`
- ❌ 文档/commit/服务器配置文件中明文 key

### 8.3 Host Bridge 文件协议安全

| 风险 | 缓解 |
|------|------|
| request_id 路径遍历 | `validate_request_id` 仅允许 `[a-zA-Z0-9_]` |
| request_file 越界 | 路径域校验：`request_file` 必须 resolve 在 `bridge_dir` 下 |
| bridge_dir 任意位置 | 默认 `skill_root/logs/host_llm_bridge/`，自动 `parents=True` 创建 |
| response 文件损坏 | 原子写入：`tempfile + os.replace`；读取时 `JSONDecodeError` 重试 ≤3 次 |
| 桥接目录权限 | 创建时 `0o700`（仅当前用户可读写） |
| 桥接目录不放敏感业务数据 | 仅 `marker + request + response + prompt`；无用户业务 |
| 子进程隔离（CI） | FakeHostRunner 走独立进程，`bridge_dir=tmp_path`，测试结束自动清理 |

**默认 bridge_dir 不污染业务**：
```
skill_root/logs/host_llm_bridge/
├── protocol.marker          # 当前待处理请求标记（单文件覆盖）
├── request_{id}.json        # 调度请求元数据
├── request_{id}.prompt       # 完整提示词
└── response_{id}.json       # 原子回传结果
```
