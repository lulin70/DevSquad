## 2. 本轮修复的真实 Bug

1. **dispatcher size gate 三处缺陷**（`scripts/check_dispatcher_size.py`）：
   - `main()` 不接受参数，测试无法注入 argv → 改为 `main(argv: list[str] | None = None)`；
   - `_snapshot()` 用 `relative_to(REPO_ROOT)`，对 pytest `tmp_path` 抛 `ValueError` → 改为 `relative_to(source)`；
   - 无 baseline 时把全部历史超大文件误判为"新增超大文件" → 仅在 baseline 命中时比较 `loc > base`（first-run safety）。
2. **baseline key 路径约定漂移**：旧 baseline key 为 `scripts/api/models.py`，新 `_snapshot()` 产出 `api/models.py` → 用 `--write-baseline` 重新生成 297 文件，key 与生产 gate 一致。
3. **Bandit 测试 schema 错误**（`tests/test_check_bandit.py`）：断言用 `totals["HIGH"]`，真实 Bandit JSON 为 `totals["SEVERITY.HIGH"]` → 按真实 schema 修复。

## 3. 教训（Lessons Learned）

- **L-V460-001（gate 脚本必须支持 argv 注入）**: CI gate 脚本的 `main()` 一律写成 `main(argv: list[str] | None = None)`，否则测试只能靠 monkeypatch subprocess 间接验证，覆盖成本高且脆。
- **L-V460-002（相对路径锚点选扫描根而非仓库根）**: `_snapshot()` 的 `relative_to` 锚点应是扫描根 `source` 而非 `REPO_ROOT`——锚点选错时，测试用 `tmp_path` 注入的目录必然抛 `ValueError`，生产路径反而测不出来。
- **L-V460-003（baseline key 约定是契约）**: baseline 文件里的 key 格式与生成代码的相对路径锚点强耦合；锚点一变 key 全变，必须重新生成并人工核对首个 key 样本，否则 gate 会在"全部文件都是新增"的假阳性上失真。
- **L-V460-004（first-run safety 是 net-growth-only 的前提）**: "只阻断净增长"策略依赖"无 baseline 不比较"语义；若首跑就把 16 个历史超大文件判为新增，gate 会立即假红，迫使团队无审计地重写 baseline。
- **L-V460-005（测试断言第三方 JSON 必须用真实 schema）**: Bandit 1.9.x 的 metrics 使用 `SEVERITY.HIGH` 键名；凭旧格式记忆写断言会让测试与实现同错。修复方向是让测试对齐真实 schema，而不是反向迁就错误断言。
- **L-V460-006（运维文档不得声明未接线的指标）**: 初版 ALERT_RULES §12 写了 3 个 Prometheus alert 表达式，但这些 gate 实际由 CI 命令判定、无 runtime exporter——文档表达超出实现即是失真。已校正为"CI/release gate 失败事件"语义，并留下未来 exporter 的 5 条接线约束。教训：写运维告警前先回答"这个 series 由谁在哪个进程里产生"。
- **L-V460-007（perf gate 有两条实现路径，文档必须区分）**: 顶层 `scripts/perf_baseline.py` 是重新测量并写 JSON 的工具；release 比较型 gate 是 `tests/test_perf_baseline_ci_gate.py`（走 `scripts.collaboration.perf_baseline`）。RUNBOOK/ROLLBACK 已明确不得把重新测量结果当作已批准的新基线。
