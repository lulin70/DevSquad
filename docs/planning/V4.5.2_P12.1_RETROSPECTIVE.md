## 3. 关键教训 (Key Lessons)

### 3.1 P1-P12 是每次迭代独立走完整周期

**教训**: 4 次迭代 (V4.5.2/3/4/5) 各自独立走 P1-P12，不是把 4 次迭代当作 P1-P12 的 4 个阶段。

**错误理解**: 我曾将 P12 (自进化闭环) 视为覆盖整个 4 迭代序列的最后一个阶段，每个迭代只走 P1-P3。

**正确理解**: 每个 V4.5.x 迭代独立走完整 P1-P12：
- P1-P2: 需求 + 共识
- P3-P5: 设计 + 测试 + 实现
- P6: 验证 (ruff/mypy/full regression)
- P7: 文档先行 (CHANGELOG/VERSION_HISTORY/release_notes)
- P8: Anti-Ghost 门禁
- P9: 发布 (commit + tag + push)
- P10: 部署 (artifacts)
- P11: 运维保障 (ALERT/RUNBOOK/ROLLBACK)
- P12: 自进化闭环 (回顾 + 教训入库)

**已写入 CarryMem**: storage_key `cm_20260821233435_6fb18ce7` (decision 类型, importance 0.72)。

### 3.2 MOKA URL 必须用官方域名

**教训**: MOKA AI 的官方 Base URL 是 `https://api.moka-ai.com/v1`（OpenAI 兼容）。常见错误：
- ❌ `https://api.moka.ai/v1` (域名错误)
- ❌ `https://api.deepseek.com/v1` (混淆)
- ✅ `https://api.moka-ai.com/v1` (官方)

**修复**: `MOKA_DEFAULT_BASE_URL = "https://api.moka-ai.com/v1"` in `moka_backend.py`。

**已写入 CarryMem**: storage_key `cm_20260821233436_b8cd3e3f` (user_preference 类型, importance 0.66)。

### 3.3 测试默认值必须用 setup_method 清理环境变量

**教训**: `MOKA_MODEL`、`MOKA_BASE_URL`、`ANTHROPIC_API_KEY` 等环境变量若在 shell 继承，会让默认模型/URL 断言失败。

**模式**:
```python
def setup_method(self):
    for k in ("MOKA_MODEL", "MOKA_BASE_URL", "MOKA_API_BASE"):
        os.environ.pop(k, None)
```

**已写入 CarryMem**: storage_key `cm_20260821233436_09c7b38f` (decision 类型, importance 0.84)。

### 3.4 MOKA 显式 backend 不再 alias OpenAIBackend

**教训**: 之前 `create_backend("moka")` 返回 `OpenAIBackend` (配置了 MOKA endpoint)；P12.1.1 改为返回 `MokaAIBackend` 实例，符合 Open/Closed 原则。

**影响**:
- `isinstance(backend, OpenAIBackend)` 在 MOKA 场景不再成立
- 测试需要更新：`assert isinstance(backend, MokaAIBackend)`
- 用户代码如果 isinstance 判断，需更新

**向后兼容**:
- `DEVSQUAD_LLM_BACKEND=moka` 仍工作（行为变了，但 API 一致）
- 旧测试需要更新断言

### 3.5 Anti-Ghost 门禁必须延伸到所有新模块

**教训**: P12.1 新增 3 个模块（MokaAIBackend, GitLabConnector, BackendConfig），每个都有 `_call_counter`，但**默认的 check_module_activation.py 只检查 5 个 V4.5.2 核心模块**。

**必须**: 每次新增模块后，更新 `scripts/check_module_activation.py` 增加对应的激活检查（import + representative call + counter read）。

### 3.6 CLI 子命令注册容易遗漏

**教训**: 三个新子命令 (metrics/doctor/backend) 在 `scripts/cli.py` 中需要：
1. `subparsers.add_parser(...)` 注册
2. `elif args.command == "...": return cmd_xxx(args)` 路由

容易遗漏路由（registration 不会触发 ImportError，运行时才崩）。P12.1 中我曾遗漏 `backend` 子命令的 routing，导致 `devsquad backend set moka` 失败。

**修复**: `elif args.command == "backend": return cmd_backend(args)` 已在 scripts/cli.py:571-572 注册。

### 3.7 ruff SIM108 (ternary) 强制改写 if-else 块

**教训**: pyproject.toml `select = [..., "SIM", ...]` 包含 SIM108，会强制把简单 if-else 块改写为三元表达式。可以用 `noqa: SIM108` 局部豁免（带注释说明为什么需要 if-else 的可读性）。

### 3.8 backend_config.py 类型注解导致 mypy no-any-return

**教训**: `load_backend_config()` 返回 `dict[str, Any]`，`resolve_backend()` 需要从这个 dict 取值并返回 `str`。直接 `return cfg["backend"]` 会触发 mypy `[no-any-return]` 错误，因为 Any 不能直接返回为 str。

**修复模式**:
```python
backend = cfg.get("backend")
if isinstance(backend, str) and backend in VALID_BACKENDS:
    return backend
```

### 3.9 _parse_yaml_simple 简化版的边界

**教训**: backend_config.py 的 `_parse_yaml_simple` 只支持 `key: value` 格式，不能解析嵌套结构。这是设计选择（P12.1 范围），未来若需要复杂配置，应该切换到 `pyyaml`。

### 3.10 GitLabConnector 共享 connector_framework 计数器

**教训**: GitLabConnector 设计选择与父 framework 共享 `_call_counter`，简化 CI 门禁。但用户可能期望"GitLab only" counter。**当前 P12.1 状态**: 两者都暴露 (`connector_framework.get_call_count()` 包含 GitHub+GitLab；`gitlab_connector.get_call_count()` 只含 GitLab)。

## 6. 经验法则 (Heuristics) 提炼

1. **每个 V*.x 迭代独立走 P1-P12**（不再合并阶段）
2. **新增模块必须更新 check_module_activation.py**（不能漏）
3. **MOKA URL 严格使用 `https://api.moka-ai.com/v1`**（三个常见错误 URL 已记入 CarryMem）
4. **测试默认值必须 setup_method 清理 env**（避免 shell 继承污染）
5. **CLI 子命令 registration + routing 两处都不能漏**（双检查点）
6. **CI 门禁失败立刻修复**（不要"下次再说"——anti-ghost 失守 = 幽灵功能风险）
