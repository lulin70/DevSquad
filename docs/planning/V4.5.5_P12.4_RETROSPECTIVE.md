## 3. 新发现教训 (L-V455-001 ~ L-V455-006)

### L-V455-001: 数据类状态保护要用 `__slots__` + property setter 双管

**现象**: `DispatchTransaction.failed_reason` 最初是 readonly property，但 `transaction_context()` 需要在 except 分支中写入。

**修复**: 增加 `@failed_reason.setter` 包装。

**教训**:
- 纯 readonly property 会在外部赋值时 raise `AttributeError: property has no setter`
- 当状态需要被 `contextmanager` 在异常分支中回填时，必须提供 setter
- 或采用 `_failed_reason` 私有 + public 方法包装（如 `set_failed_reason()`），但前者更 Pythonic

**应用到 V4.5.6**: 所有"context manager 异常回填"的字段都必须有 setter 或写方法

### L-V455-002: `ALLOWED_TRANSITIONS` 表驱动 FSM 比 if/elif 更易测试

**现象**: V4.5.4 ModuleFiber 用 6 状态 dict + 比较常量。V4.5.6 DispatchTransaction 用 `ALLOWED_TRANSITIONS: dict[TxState, frozenset[TxState]]` 表驱动。

**对比**:
```python
# V4.5.4 风格 (if/elif)
if self._state == TxState.ACTIVE:
    if new_state not in (TxState.COMMITTED, TxState.ROLLED_BACK, TxState.FAILED):
        raise TxStateError(...)

# V4.5.6 风格 (表驱动)
_validate_transition(self._state, new_state)  # 一行
```

**教训**:
- FSM 状态 > 4 时，if/elif 链臃肿且难测试边界条件
- `frozenset` 提供 O(1) 查询 + 不可变保证
- 测试只需 `pytest.mark.parametrize` 遍历 ALLOWED_TRANSITIONS 即可

**应用到 V4.5.6**: 任何 > 3 状态的 FSM 都用表驱动

### L-V455-003: `fail()` 方法不能 strict raise，否则破坏 resilience

**现象**: 最初 `fail()` 实现为 `raise TxStateError if not allowed`，但 `transaction_context()` 在 except 分支调用 fail()，如果已经在 FAILED 状态再 fail，会触发异常抛到上层，导致 cleanup 中断。

**修复**: `fail()` 用 `with suppress(TxStateError):` 静默无效转移，但总是把 `_state` 强制设到 FAILED 并记录 reason（resilience 优先）。

**教训**:
- "终态保护"和"resilience cleanup"是冲突的
- fail() 应该总是成功（不抛异常），invalid transition 静默忽略
- 严格 FSM 校验应该放在 commit/rollback 等用户显式调用的方法上

**应用到 V4.5.6**: cleanup 类方法用 `suppress` 容忍所有错误，user-facing 方法严格校验

### L-V455-004: `request_file` 越界校验必须用 `os.path.commonpath` 而不是字符串前缀

**现象**: 最初考虑用 `request_file.startswith(bridge_dir)` 但 `/tmp/host_bridge` 是 `/tmp/host_bridge_evil` 的前缀，会误判。

**修复**: `os.path.commonpath([abs_req, abs_bridge]) == abs_bridge` 是正确语义。

**教训**:
- 字符串前缀易被绕过（`/tmp/host_bridge_evil/` 通过 `/tmp/host_bridge` 校验）
- `os.path.commonpath` 是正确语义（路径分量级别比较）
- 但 `commonpath` 在不同盘符会 raise ValueError（Windows），必须 try/except

**应用到 V4.5.6**: 任何 path containment check 优先用 `commonpath` 而非字符串前缀

### L-V455-005: Reason 标准化哈希必须 ignore case + trim + truncate

**现象**: 测试 `LoopController.should_stop()` 时，连续两次 `"  TIMEOUT  "` 和 `"timeout"` 应该算"相同 reason"（都是 timeout），否则 fuse 永远不触发。

**修复**: `_normalize_reason()` 实现为 `reason.strip().lower()[:50]`，并兜底 "unknown"。

**教训**:
- exception message 常带前后空格 + 大小写不一致
- truncate 到 50 字符防止病理差异（如内存地址）
- 用 try/except 兜底（V4.5.3 lesson #7）：reason 不是字符串时返回 "unknown"

**应用到 V4.5.6**: 任何"连续 N 次相同 X"的判等都用标准化哈希

### L-V455-006: Anti-Ghost counter 必须在导入时 import 别名绑定到 main scope

**现象**: V4.5.4 `_activate_v454_modules()` 用 `from module import get_call_counter_er` 在函数内 import，但 local scope 内的 import 在 counter 已存在后不影响 main scope 调用。

**修复**: V4.5.6 在 `main()` 内 `from ... import get_call_counter_er as _get_*` 在顶层绑定，然后 counters dict 用别名。

**教训**:
- Anti-Ghost counter 必须有 get_call_counter 函数对外暴露
- 多个模块各自维护 counter，但 `check_module_activation.py` 必须能用一个函数名取到所有 counter
- 推荐模式：每个模块 export `get_call_counter_er()`，main 用 `as` 别名统一调度

**应用到 V4.5.6**: 所有 anti-ghost 验证都用 main scope 预 import + 别名模式
