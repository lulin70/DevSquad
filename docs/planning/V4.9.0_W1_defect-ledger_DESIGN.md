## 1. 设计目标

1. 缺陷成为跨 run 生命周期对象：run 结束后可立案、可追踪、可回归核对。
2. 封闭状态机 + 每转移强制字段，杜绝口头关闭。
3. 上游两坑（转移丢失 / ID 复用）在实现层不可复现（PRD §5 直写要求）。
4. 纯标准库、零新依赖、零 LLM（确定性侧资产）。

## 2. 关键裁定（含开放点③）

| 裁定项 | 决定 | 理由 |
|---|---|---|
| 台账落点 | **`.devsquad/defects.json`**（项目级单文件） | `.devsquad/` 项目状态目录惯例已存在（[cli.py:674](../../scripts/cli.py#L674) `--project`）；跨 run 全局；不污染仓库根 |
| 命令挂载（开放点③） | **顶层子命令 `devsquad defect`**（与 dispatch/status 平级，非 lifecycle 子命令） | 台账跨 spec→ship 全生命周期，不隶属单一生命周期命令；PRD §9 倾向一致 |
| 模块落点 | `scripts/collaboration/defect_ledger.py`（新模块，纯 stdlib） | 与 tech_debt_manager.py 同层同模式（dataclass + to_dict/from_dict） |
| 版本协商 | `schema_version: 1` 字段；不识别的版本 → 拒绝加载（fail-closed，提示升级） | 前向演进留钩子；不静默降级 |
| 台账入库与否 | 工具不强制；本仓 dogfood 时提交入库（证据链），外部项目自便 | 与 TECH_DEBT.md 管理口径一致 |

## 3. Schema（v1）

```json
{
  "schema_version": 1,
  "next_id": 5,
  "entries": [
    {
      "id": "DEF-001",
      "state": "open",
      "signal": {
        "type": "review:break-vuln:BREAK-2",
        "ref": "audit:event=42&finding=1",
        "summary": "handler without return in api/routes/dispatch.py",
        "captured_at": "2026-10-25T10:00:00+08:00"
      },
      "fix": null,
      "regression": null,
      "reopen_reason": null,
      "created_at": "2026-10-25T10:05:00+08:00",
      "history": [
        {"transition": "create", "to": "open", "at": "…", "fields": {"signal_type": "review:break-vuln:BREAK-2"}}
      ]
    }
  ]
}
```

- **state**：封闭集 `open | fixed | closed`（三态；regressed 是 closed→open 的转移原因，非独立态——与上游模型一致，PRD §4.1）。
- **next_id**：单调递增分配计数器，与条目同一次原子写持久化。**永不回退**：即使条目被手工删除，next_id 不降 → 已分配 ID 永不回收（坑 2 主防线）。
- **history**：每条目转移记录追加式数组（前/后状态、时间戳、强制字段值）；reopen 清空 fix/regression 前，旧值完整记入 history（信息不丢，PRD §5 坑 1.4）。
- 条目当前 state 是 history 尾部的派生视图。

## 4. 状态机与命令面

### 4.1 转移表（每转移强制字段，其余一律拒绝）

| 转移 | 命令 | 强制字段 | 语义 |
|---|---|---|---|
| create→open | `defect add --signal-ref R --summary S` | signal_ref、summary | 立案；signal_ref 必须解析成功（禁凭空立案，解析见 §5） |
| open→fixed | `defect update <ID> --commit SHA --summary S` | fix commit SHA、fix summary | 登记修复 |
| fixed→fixed | 同 update（重登记） | 同上 | 修复迭代（回归前发现新问题→补新 commit） |
| fixed→closed | `defect close <ID> --run-ref R` | regression run ref | 关闭前核对：run 引用解析成功且该 run 无 product_failed 信号、无 critical findings（§5.2）；解析失败或核对不过 → 拒绝（禁口头关闭） |
| closed→open | `defect reopen <ID> --reason R` | reopen reason | 回炉；清空 fix/regression（旧值入 history） |
| （禁止）open→closed、closed→fixed、fixed→open | — | — | 跳态/逆序一律拒绝并报错 |

### 4.2 命令面

```
devsquad defect add    --signal-ref R --summary S [--json]
devsquad defect update <DEF-NNN> --commit SHA --summary S [--json]
devsquad defect close   <DEF-NNN> --run-ref R [--json]
devsquad defect reopen  <DEF-NNN> --reason R [--json]
devsquad defect list    [--state open|fixed|closed] [--json]
devsquad defect audit   [--json]
```

- 全部子命令 exit 0/1/2 契约（failure_taxonomy C19：product_failed=1 / environment_blocked=2）。
- 无 delete 子命令（PRD §4.1：封闭生命周期，v1 无删除面）。
- 挂载实现：[cli.py](../../scripts/cli.py) `add_parser("defect")` + 子子命令（模式同 `sessions`/`backend` 嵌套组，锚点 cli.py:651-680）。

## 5. 信号引用与关闭核对（W1 契约面）

### 5.1 signal_ref 解析（v1 唯一格式：dispatch audit 链）

`audit:event=<N>&finding=<i>`（review finding）/ `audit:event=<N>&failure=<class>`（FailureClass 记录）。

- 解析源：`audit/dispatch_audit.db`（SQLite 哈希链，[dispatch_audit.py:189-198](../../scripts/collaboration/dispatch_audit.py#L189-L198) 表结构；findings/failure_class 在事件 `details` JSON 内）。
- 解析规则：event N 必须存在且 finding 索引/失败分类在 details 内可定位；否则 add 拒绝（负向测试 ①，PRD §7）。
- 格式前缀 `audit:` 留扩展位：W2 若增加 review diff 通道信号源（如 `review:<artifact>`），不改 schema。

### 5.2 close 的回归核对

- `--run-ref` 同样为 `audit:event=<N>` 格式；close 读取该事件 details：存在 product_failed 信号或 critical finding → 拒绝关闭；环境阻断（environment_blocked）不计入。
- 无可用 audit DB（未跑过 dispatch 的项目）→ close 拒绝并提示先跑回归 run（fail-closed，不提供"跳过核对"后门）。

## 6. 两坑防护实现（PRD §5 落地）

### 6.1 坑 1 转移丢失

1. **原子写**：同目录 tempfile 写入 → `os.fsync` → `os.replace` 原子替换；杜绝半写。
2. **加载校验 fail-closed**：每次命令执行前加载台账并校验——每条目 `state` == 其 history 最后一条转移的 `to`；next_id > 所有出现过的 ID；ID 无重复。任何不一致 → 该次命令非零退出 + 违规明细（绝不静默修复）。
3. **history 追加不可变**：转移 = 追加 history 记录 + 重建条目视图 + 整文件原子写（单文件无部分提交面）。

### 6.2 坑 2 ID 复用

1. 分配仅经 `next_id`（与条目同一原子写事务）；不扫描"现存条目取 max"（上游错误模式）。
2. `defect audit` 交叉核验：条目 ID 唯一、全部 < next_id、每个条目 history 含 create 记录。
3. 手工指定 ID（add 不提供 --id 参数）面不存在 → 复用入口只剩手工编辑文件，由 6.1.2 加载校验拦截。

## 7. 测试设计（W1 单测面，阶段 2 出口）

- **全转移覆盖**：4 条合法转移 + 重登记 + 3 类非法转移拒绝，逐条断言（含拒绝原因文本）。
- **负向先行**（PRD §7 前五项在 W1 的落点）：无信号立案被拒（§5.1）；ID 复用防护（篡改 next_id 回退 → 加载校验红）；状态-history 脱节 → fail-closed；半写文件（截断 JSON）→ 拒载；关闭核对不过（回归 run 含 product_failed）→ 拒绝。
- **原子性**：monkeypatch os.replace 抛错 → 台账文件内容不变（转移丢失不可复现）。
- **JSON 往返**：schema_roundtrip（to_dict/from_dict 保真，参照 tech_debt_manager 测试模式）。
- 用真实 `sqlite3` 临时库构造 audit 事件做信号解析测试（不用 Mock 造 details，用户测试原则）。
