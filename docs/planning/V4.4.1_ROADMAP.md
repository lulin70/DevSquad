## 2. P3-1: Real User Testing Plan

### 2.1 Objective

Validate DevSquad V4.4.0 with 3-5 real users (developers/PMs/DevOps) to:
- Verify the 5 new modules (Risk Register / Viewpoint Registry / Error Budget / Gap Analyzer / DORA Metrics) deliver user-visible value
- Identify UX friction in dispatch pipeline integration
- Collect NPS and qualitative feedback for V4.5.0 priorities

### 2.2 Test Scenarios (based on V4.3.0 P3-5 AI-simulated journeys)

| # | Role | Scenario | V4.4.0 Module Exercised | Success Criteria |
|---|------|----------|------------------------|------------------|
| RU-1 | PM | "Design user auth system for mobile app" → dispatch → review risk register section in report | RiskRegister | User sees "## Risk Management" section with ≥3 risks, exposure sorted desc |
| RU-2 | Architect | "Review microservice architecture" → dispatch → check viewpoint consistency | ViewpointRegistry | User can identify which roles have orthogonal vs overlapping concerns |
| RU-3 | DevOps | "Plan deployment for V4.4.0" → P10 gate → error budget check | ErrorBudgetTracker | User sees budget status (HEALTHY/BURNING_FAST/EXHAUSTED) in gate result |
| RU-4 | Developer | "Analyze gap between current and target architecture" → dispatch → review roadmap | GapAnalyzer | User sees Markdown roadmap table with phases and priorities |
| RU-5 | DevOps | "Collect DORA metrics for last 30 days" → P11 gate → CFR check | DoraMetricsCollector | User sees 4 DORA metrics + Elite/High/Medium/Low rating |

### 2.3 Participant Recruitment

| Role | Count | Source | Compensation |
|------|-------|--------|-------------|
| PM | 1-2 | Internal team / beta users | N/A (internal) |
| Developer | 1-2 | Internal team / open-source contributors | N/A |
| DevOps | 1 | Internal team | N/A |

Target: 3-5 participants (Nielsen's 5-user rule for usability testing).

### 2.4 Test Protocol

1. **Pre-test briefing** (5 min): Explain DevSquad purpose, no right/wrong answers
2. **Task execution** (20 min): User completes 2-3 scenarios from §2.2 using CLI/API
3. **Think-aloud** (during): User verbalizes thought process, observer takes notes
4. **Post-test interview** (10 min): NPS score, friction points, improvement suggestions
5. **Report generation** (automated): DevSquad dispatch report reviewed for module visibility

### 2.5 Acceptance Criteria

| ID | Criterion | Measurement |
|----|-----------|-------------|
| AC-1 | All 5 V4.4.0 modules produce user-visible output | Manual: user confirms seeing each module's section in report |
| AC-2 | NPS ≥ 7 (promoter threshold) | Post-test survey |
| AC-3 | Task completion rate ≥ 80% | Observer: user completes scenario without researcher intervention |
| AC-4 | No critical UX blocker identified | Post-test interview analysis |
| AC-5 | Anti-ghost verification passes in real dispatch | E2E test E13 counter > 0 for all 5 modules |

## 3. P3-2: Performance Baseline (Implemented in V4.4.1)

### 3.1 Implementation

CI nightly `performance` job added (`.github/workflows/test.yml`):
- **Trigger**: nightly schedule (`0 2 * * *`) + manual dispatch
- **Scope**: `tests/test_performance_benchmarks.py` + `tests/test_v39_performance.py` (23 tests)
- **Blocking**: non-blocking (informational only) — V4.4.2+ may promote to blocking after baseline establishment
- **Artifact**: performance log + JUnit XML (30-day retention for trend analysis)

### 3.2 Rationale for Non-blocking

project_memory lesson: "CI runner 性能波动: GitHub Actions hosted runners 比本地慢 5-10x". Performance thresholds (e.g. `under_50ms`) may fail on CI runners. Non-blocking allows baseline collection without false-positive CI failures.

### 3.3 V4.4.2+ Promotion Criteria

Performance gate promoted to blocking when:
1. 30 days of nightly baseline data collected
2. P95 latency measured on CI runners (not local)
3. Thresholds adjusted with 10x margin per project_memory lesson
4. `BenchmarkRegressionChecker` integrated as P11 lifecycle gate

## 4. P2-1: mypy Version Drift Fix (Implemented in V4.4.1)

### 4.1 Problem

V4.4.0 7-dimension assessment incorrectly reported "1 error in numpy stub". Actual issue: local mypy 1.19.1 vs CI mypy 2.2.0 version drift, causing 10 errors locally that don't appear in CI.

### 4.2 Fix

- `requirements-dev.txt`: pinned `mypy==2.2.0`, `ruff==0.15.20`, `black==26.5.1`, `radon==6.0.1` (matching `requirements-dev.lock`)
- `pyproject.toml [dev]`: pinned same versions for `pip install -e ".[dev]"`
- Local `pip install -r requirements-dev.txt` now matches CI versions

### 4.3 Verification

```bash
pip install -r requirements-dev.txt
mypy --version  # should print 2.2.0
mypy scripts/collaboration/ --ignore-missing-imports --no-error-summary  # 0 errors
```
